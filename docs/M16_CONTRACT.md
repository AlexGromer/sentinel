# Контракт M16 — «Всё через UI»: три равноправные поверхности и чат как центр продукта

> 🌐 **Русский** (основная версия) · [English](M16_CONTRACT.en.md)

Предлагает **ADR-107…110**. Статус всех четырёх — **Proposed**; в таблицу `ARCHITECTURE.md §3`
вносятся при принятии.

Директивы Alex, задавшие этот контракт (2026-07-29):

> «ВСЁ ДОЛЖНО БЫТЬ ЧЕРЕЗ UI. Только первый запуск без флагов, из CLI. Из UI должно быть возможно
> сделать всё, что и из CLI.»

> «У нас должна быть возможность конфигурации ВСЕГО СТЕКА И ВСЕХ ВЕЩЕЙ тем способом, которым захочет
> пользователь: полностью по API · полностью по UI · полностью файлами/env. А не размазана повсюду.»

---

## 1. Зачем

Продукт нарушает собственный принцип, и нарушение измерено, а не почувствовано. Ниже — замер
2026-07-29 (49 пользовательских возможностей, каждая строка с `file:line`, полная таблица —
`docs/M16_MATRIX.md`).

| поверхность | возможность отсутствует | из 49 |
|---|---|---|
| **CLI** (`agentctl`) | 20 | 41 % |
| **HTTP** (control-api) | 18 | 37 % |
| **UI** (хаб) | 23 + 5 частично | 47 % / 57 % |
| **есть на всех трёх** | **5** | **10 %** |

Разрыв **не** в том, что UI отстаёт от CLI. Дырявы все три поверхности, каждая в своём месте:

- `agentctl` — инструмент про прогон и артефакты. Всё про **хранилище и конфиг** (список и удаление
  сценариев/тестов/бесед, промоут теста, результаты, тренды, логи, чтение и запись конфига, схема,
  health) существует только по HTTP: у всех 15 «только-UI» возможностей `cli = none`.
- HTTP не несёт **git-канала, экспорта `.spec.ts`, операционных команд** (карантин, калибровка,
  редакция трейса, `purge-store`, `sweep-downloaded`) и не имеет полей для **бюджетов, `auth`,
  `scenarios`, CI-флагов** вовсе (`cmd/control-api/main.go:1061-1062`).
- UI не умеет 23 вещи, ещё 5 умеет частично, одна кнопка мертва.

Самое острое по группам: **версионирование — 4 из 4 отсутствуют в UI** (`list`/`show`/`diff`/
`rollback` есть и в CLI, и в HTTP, а в интерфейсе нет ничего); **импорт/экспорт — 5 из 6 нет ни в
UI, ни в HTTP**; **операции — 8 из 9 нет ни в UI, ни в HTTP**.

## 2. ADR-107 — конфигурация: одна модель, три полных проекции

### 2.1 Инвариант

Существует **одна** модель конфигурации. CLI, HTTP и UI — её **проекции**, а не независимые
поверхности. Возможность, доступная на одной проекции, обязана быть доступна на всех трёх.
Единственное исключение — bootstrap (§2.5).

Источник истины — расширенная схема, которую уже отдаёт `GET /v1/config-schema`
(`cmd/control-api/main.go:306`, без авторизации). Сегодня она несёт 8 блоков верхнего уровня:
`fields`, `settings`, `llm`, `modes`, `planner`, `roles`, `backends`, `note`; в `settings` — 16
настроек с группами (`gates`, `healing`, `hitl`, `retention`), двуязычными подсказками и привязкой
к переменной окружения.

**Это уже готовая основа**: схема двуязычна, сгруппирована и знает env-имя каждого ключа. Работа —
не спроектировать поверхность, а достроить схему и сгенерировать из неё три проекции.

### 2.2 Чего в схеме нет и что дописывается

| предмет | где живёт сегодня | куда переносится |
|---|---|---|
| `auth{storage_state, storage_state_save, login_plan, pw_no_trace}` | только `run.yaml` (`brain/runconfig.py:34-35`) | схема → все три проекции |
| `scenarios[{name, goal\|describe}]` | только `run.yaml` (`runconfig.py:36`) | схема → все три проекции |
| аллоулист окружения (`SENTINEL_ENV_ALLOWLIST`, `SENTINEL_ENV_ALLOW`) | только env (`cmd/agentctl/main.go:339,359-363`) | схема, помечено как security-sensitive |
| `--ci`, `--force-replay`, `--aut-version` | только флаги CLI (`main.go:487-489`) | схема + `runRequest` |
| произвольный путь к `plan.json` для replay/baseline | только `--plan` (`main.go:484-485`) | загрузка плана по HTTP |
| CDP-подключение, выбор интерпретатора brain | только env | схема |

### 2.3 Чего нет в HTTP

`runRequest` (`cmd/control-api/main.go:1061-1062`) несёт `Target, Mode, Goal, Describe, Planner,
CoverageTarget, MaxSteps, FromRun, ConversationID, LLM` — и всё.

Отсюда следует дефект, который **нельзя починить правкой UI**: форма «Новый прогон» показывает поля
бюджетов и `auth` (`docs/index.html:748-768`), но обработчик кнопки «Запустить»
(`docs/index.html:2287-2298`) их **не читает**. Вместо этого `renderBuild()`
(`docs/index.html:1783-1835`) складывает их в текст `run.yaml`, самодокументированный как «Pass via:
`--run-config <file>`». То есть интерфейс собирает файл и отправляет человека в консоль.

⇒ Кнопки `⬇ run.yaml` и `⬇ sentinel.env` — **не фича и не экспорт, а заплатка поверх дыры в
контракте API**. После дополнения `runRequest` они остаются, но меняют смысл и имя: «экспорт
конфигурации прогона» для воспроизведения в CI, а не обязательный путь к бюджету.

### 2.4 Чего нет в CLI

Добавляются подкоманды, покрывающие вторую половину продукта:

- `agentctl config schema|get|set` — чтение схемы и persisted-конфига, запись;
- `agentctl scenarios list|show|delete`, `agentctl tests list|show|promote|rename|delete`;
- `agentctl chats list|show|delete`;
- `agentctl results list|show`, `agentctl trends`;
- `agentctl logs --run <id> [фильтры]`;
- `agentctl health` (аналог `/healthz` + `/readyz`).

### 2.5 Единственное исключение — bootstrap

Из-под принципа выведено ровно одно: **первый запуск control-api** (адрес прослушивания, источник
токена, CORS-происхождения, путь к `agentctl`). Это `first-launch-exempt` в матрице. Сегодня
control-api **не принимает ни одного флага командной строки** и настраивается только окружением
(`CONTROL_API_ADDR`, `cmd/control-api/main.go:1937`) — это остаётся как есть.

### 2.6 Гейты

Два, и оба формулируются **свойством, а не перечнем** — правило `measure-the-capability-not-a-copy`:

1. **Гейт полноты проекций.** Для каждого ключа схемы обязана существовать проекция в CLI, в HTTP и
   в UI. Проверяется обходом схемы, а не списком известных ключей, — иначе новый ключ не попадёт в
   проверку автоматически.
2. **Гейт дрейфа снимка схемы — починить.** `TestSetupWizardSchemaSnapshotMatchesHandler`
   (`cmd/control-api/setup_wizard_test.go:89`) сверял множество ключей верхнего уровня, а затем
   спускался ровно в `modes`, `planner`, `backends`, `roles`, `fields` (`:102`) и `llm` (`:115`).
   Блок `settings` в это множество входил и потому выглядел покрытым — но его содержимое не
   сверялось никогда: подстрока `"settings"` встречалась в тесте **ноль раз**. Починка: обходить
   оба дерева, тогда любой новый блок покрыт по построению.

   Этот гейт уже пропустил дефект: офлайновый снимок мастера нёс **14** настроек против **16** в
   живой схеме — отсутствовали `run_keep` и `run_ttl_hours`. В air-gapped-режиме удержание прогонов
   было не настроить.

## 3. ADR-108 — информационная архитектура: чат как центр продукта

### 3.1 Трёхпанельный экран — только во вкладке чата

Раскладка действует **исключительно внутри вкладки конкретного чата**. В настройках, в консоли
авторинга, в инструментах, в библиотеке, в результатах её нет.

```
┌──────────────┬────────────────────────────┐
│              │  ЖИВАЯ ОБЛАСТЬ  [тумблер]  │
│    беседа    │  режим 1 / 2 / 3           │
│              │                            │
├──────────────┼────────────────────────────┤
│  цель чата   │  ХОД ПРОГОНА               │
│  (неизменна) │  шаги · события            │
│              │  [бизнес] [инструмент]     │
└──────────────┴────────────────────────────┘
```

### 3.2 Живая область и тумблер режимов

Три режима, переключаемые **тумблером без перезагрузки страницы**:

| режим | что показывает | состояние |
|---|---|---|
| **1. Вид браузера** | кадр на каждое действие | доступно сегодня: `page.screenshot()` детерминирован — фиксированный viewport, DSR=1 (`pw-executor/src/server.ts:404,888,956`) |
| **2. Действия** | список действий Playwright с DOM-снимком по выбору, как в Trace Viewer | требует стриминга снимков DOM пошагово |
| **3. Видео** | непрерывный поток из браузера | **не реализовано нигде**: `Page.startScreencast` в коде отсутствует; новая подсистема (захват, кодек, доставка, хранение) |
| *4. Сетевой трейс* | запросы, как во вкладке Network браузера | **желательно, не обязательно** (формулировка Alex: «в идеале… но ладно») |

Транспорт — уже существующий WS `/v1/stream` (ADR-043/054).

**Терминологическая честность.** `trace.zip` — собственный формат Playwright, дописываемый **при
закрытии контекста** (`pw-executor/src/server.ts:439`); стримить его нельзя по построению. Он
**остаётся как есть** — скачивание и просмотр после прогона. Живые режимы 1–3 — отдельный предмет,
и называть их «live trace» в документации запрещено во избежание того же смешения.

**Ограничение по редакции.** Пиксели не редактируются (ADR-098, `server.ts:432-433`). Режимы 1–3
подчиняются тому же переключателю, что и скриншоты трейса
(`SENTINEL_TRACE_SCREENSHOTS`), и режиму no-secrets (§3.8).

### 3.3 Ход прогона и видимое разделение логов

Нижняя правая панель показывает шаги и события прогона с **видимым** разделением
«бизнес-логика ↔ инструмент».

Механизм **уже построен и работает целиком**: слой `audiences` в `brain/events.json`
(`business` = {`application`, `testing`}, `tool` = {`tool`}) → отдаётся через
`GET /v1/events-catalog` → в хабе строятся `<optgroup>` (`docs/index.html:3405-3428`), а язык
фильтров принимает имя аудитории как объединение источников (`:3264-3265`). Проверено живым
запросом к control-api.

**Не сделано представление.** Сегодня разделение существует как *значение фильтра* в выпадающем
списке «Источник» внутри отдельной вкладки «Логи»: чтобы его увидеть, надо догадаться открыть
вкладку, раскрыть список и выбрать «бизнес-логика». На экране ничто не сообщает, что логов два рода.
В живом таймлайне фильтра по источнику **нет вообще** — в разметке live-вью он отсутствует.

⇒ Требование: разделение становится **представлением** (две явные дорожки либо переключатель на
виду), а не спрятанным фильтром, и присутствует там, где человек реально смотрит за прогоном.

### 3.4 Цель принадлежит чату

- Цель фиксируется за **беседой целиком**, а не за прогоном.
- **Сменить цель нельзя.** Для новой цели — новый чат.
- Схема: `chats.last_goal` (изменяемое «последнее», `internal/store/server.go:60-63`) заменяется
  неизменяемым `goal`, устанавливаемым один раз при создании беседы; попытка смены отклоняется.

### 3.5 Два входа, один центр

1. **Через консоль авторинга.** Консоль остаётся. По завершении она **перебрасывает в чат**, где
   продолжается общение и идёт корректировка.
2. **Прямо в чате.** Новая беседа: человек даёт ссылку и описывает задачу словами → запускаются все
   механизмы, без захода в консоль.

Работа из любого места — одна и та же цепочка.

Замечание по именованию: сегодня вкладка объявлена `data-view="chat"`, но её внутреннее имя —
`data-subpanel="author"` (`docs/index.html:889`), и содержимое — форма авторинга (режим, target,
«опиши поток») с кнопками прогона. То есть «Запустить/Перепрогон/Эталон» стоят там **уместно** —
неверно название. После M16 это разделяется физически: консоль авторинга и чат — разные вкладки.

### 3.6 Без цели разговора нет

Если человек просто беседует, не задав цели, модель отвечает требованием задать цель. Свободный
разговор без цели продуктом не поддерживается.

### 3.7 Гейт карты: доложить и спросить

После этапа explore и построения карты инструмент **сам анализирует карту**, докладывает результат
человеку и **спрашивает разрешение** идти дальше. До ответа следующие шаги не выполняются.

Шов существует: `SENTINEL_AUTO_HITL_THRESHOLD` уже поднимает `hitl_needed` как сигнал, а
takeover/return реализованы (ADR-054, `ws.go:199`). Новое здесь — **безусловная точка останова после
explore** (не по счётчику неудач) и **содержательный доклад о карте**, а не голое «требуется
человек».

### 3.8 Артефакты и режимы

- Артефакты **скачиваются прямо из чата** и **просматриваются через canvas** — панель просмотра
  внутри беседы, как в чатах других моделей. Выдача уже есть: `GET /v1/runs/{id}/artifact`
  (по белому списку, `cmd/control-api/main.go:1276`).
- **Все режимы — переключателями в настройках**, включая no-secrets. Не переменными окружения, не
  флагами: тумблерами на экране, при сохранении полного паритета с API и файлами (§2.1).

### 3.9 Исключение

Раскладка и живые режимы не применяются, когда человек работает **из расширения браузера** или
**передал управление собственным браузером** — там источник картинки его, а не наш.

### 3.10 Что здесь новое, а что доработка

**Новая подсистема:** полноценный многоходовый разговор с LLM. Сегодня его нет как класса —
`POST /v1/chat/completions` есть один ход → один прогон (ADR-041), а multi-turn `conversation_id`
уточняет сценарий, но не ведёт беседу (зафиксировано в `BACKLOG.md:82`). Это не доработка чата, это
его появление.

**Доработка:** живая область (транспорт есть), ход прогона (события есть), разделение логов
(механизм есть, нет представления), артефакты (выдача есть), гейт карты (шов есть).

## 4. ADR-109 — локальная идентичность в ядре; ревизия ADR-056

### 4.1 Решение Alex

> «По авторизации — в коммерцию уйдёт всякое типа OIDC, а для opensource делаем локальную
> авторизацию.»

| предмет | лицензия |
|---|---|
| локальные учётные записи, вход, свои беседы/прогоны/сценарии у каждого | **OSS (Apache)** |
| OIDC/SSO/RBAC, мультитенантность, корпоративные каталоги | **COMM** |

### 4.2 Это изменение модели данных, а не middleware

Сегодня субъекта нет **нигде**. Проверено по схеме (`internal/store/server.go:27-77`): восемь таблиц
(`runs`, `scenarios`, `tests`, `chats`, `results`, `metrics`, `config` + легаси) — **ни одной колонки
владельца**. `config` — глобальный key-value на весь инстанс. Аутентификация — один общий bearer,
сравниваемый в постоянное время (`cmd/control-api/main.go:288-292`), fail-closed при пустом токене.
Все совпадения слова `role` в коде — это ARIA-роли, роли сообщений чата и per-role оверрайд модели.

⇒ Требуется субъект в `runs`, `scenarios`, `tests`, `chats`, `results` и разделение `config` на
глобальный и пользовательский. Без этого требование «у каждого свой набор чатов» невыразимо.

### 4.3 Ревизия ADR-056

ADR-056 сейчас относит **multi-user целиком** в commercial-reserve («enterprise-auth
(SSO/RBAC/multi-user)», `ARCHITECTURE.md:187`). Решение §4.1 этому противоречит и **требует правки
ADR-056**, а не ссылки на него. Основание для правки — собственный принцип ADR-056: «open-core =
ПОЛНЫЙ полезный инструмент для одной команды, НЕ crippleware»; команда из нескольких человек без
разделения данных — это crippleware.

## 5. ADR-110 — поставка

### 5.1 Замер

Конвейер релиза **готов целиком и не срабатывал ни разу**:

| факт | доказательство |
|---|---|
| 30 бинарей (5 бинарей × 6 платформ), multi-arch образ в GHCR, cosign keyless, CycloneDX SBOM, GitHub Release со всеми ассетами | `.github/workflows/release.yml:1-6,21,100-166` |
| триггер — только тег `v*` | `release.yml:13-15` |
| тегов **ноль** локально и на remote | `git tag --list`, `git ls-remote --tags origin` |
| `install.sh` резолвит `latest` через GitHub API | `install.sh:43` — упрётся в пустой список |
| `Formula/sentinel.rb` — намеренная заглушка `v0.0.0`, нулевой sha256 | `Formula/sentinel.rb:3-4,8,13-18` |
| `docker-compose.yml` только `build:` из исходников | `docker-compose.yml:17-19` |

⇒ **Все три пути установки сегодня мертвы, и причина у всех одна.** Это не стройка, а **один
подписанный тег**. `workflow_dispatch` умеет холостой прогон (сборка + SBOM без пуша и подписи), то
есть конвейер проверяется до тега.

### 5.2 Объём

1. Холостой прогон `workflow_dispatch` → убедиться, что конвейер зелёный.
2. Первый подписанный тег `v0.1.0` → GitHub Release, образ в GHCR, рабочие `install.sh` и brew.
3. `docker-compose.yml` — вариант с `image:` из GHCR вместо сборки из исходников.
4. **podman** (проверить `docker-compose.yml` под `podman-compose`, назвать расхождения).
5. **deb/apt** — сегодня отсутствует; искал `nfpm`, `goreleaser`, `fpm`, `debian/`, `packaging/` —
   есть только `Formula/sentinel.rb`.
6. **Честный баннер на GitHub Pages**: статическая витрина обязана говорить, что она витрина, и
   гасить (не показывать рабочими) элементы, за которыми нет бэкенда.

## 6. Дефекты, найденные замером и подлежащие починке

## 7. Отложено и открыто

- **Сетевой трейс** (режим 4, §3.2) — желателен, в обязательный объём M16 не входит.
- **Видео (режим 3)** — новая подсистема; требует отдельного решения по хранению и редакции пикселей.
- **Реестр бэклога.** `mcp__backlog-mcp__*` **непригоден для этого файла**: парсер требует, чтобы
  строка заканчивалась датой в формате `(P2) @agent — YYYY-MM-DD`, и знает только `[ ]`, `[x]`, `[X]`
  (`~/.claude/mcp-servers/backlog-mcp/parser.go:26-36`). Наши записи повествовательные и
  трёхсостоянийные (`[~]` — 9 штук), поэтому MCP видит **11 задач из 126** и считает Active пустым.
  До починки парсера реестр правится вручную. Это работа в конфигурации, вне Sentinel.

## 8. Критерии приёмки

1. **Полнота проекций.** Для каждого ключа схемы существует проекция в CLI, HTTP и UI; проверяется
   обходом схемы, а не списком ключей. Матрица `docs/M16_MATRIX.md` пересчитывается: строк с
   вердиктом `ui-missing`, `ui-partial`, `ui-only`, `dead-in-ui` — ноль, кроме `first-launch-exempt`.
2. **Гейт дрейфа** сверяет множество ключей верхнего уровня схемы и рекурсивно все блоки; добавление
   нового блока без обновления снимка мастера роняет тест.
3. **Чат.** Многоходовый разговор с LLM ведётся; цель принадлежит беседе и не меняется; попытка смены
   отклоняется гейтом; оба входа (консоль → чат, ссылка в чате) приводят к одной цепочке; беседа без
   цели отвечает требованием задать цель.
4. **Трёхпанельный экран** присутствует во вкладке чата и отсутствует во всех прочих вью; тумблер
   переключает режимы живой области **без перезагрузки страницы**.
5. **Разделение логов видно на экране** в ходе прогона, а не только как значение фильтра.
6. **Гейт карты**: после explore прогон останавливается, докладывает разбор карты и ждёт разрешения;
   без ответа следующий шаг не выполняется.
7. **Артефакты** скачиваются из чата и открываются в canvas.
8. **Идентичность**: два локальных пользователя видят разные наборы бесед, прогонов и сценариев;
   `config` разделён на глобальный и пользовательский.
9. **Поставка**: с чистой машины без Go/Node/Python установка проходит одним из путей (скрипт, brew,
   образ) и поднимает UI; на GitHub Pages витрина честно объявлена витриной.
10. **Дефекты §6 (1–4)** закрыты, каждый — поведенческим гейтом с мутационной проверкой.
