## Обзор

Sentinel работает с двумя отдельными уровнями памяти с намеренно разграниченным владением:
**краткосрочная эпизодическая память**, сохраняемая Python LangGraph brain в собственную базу данных
checkpoint, и **долгосрочная межсессионная память**, принадлежащая исключительно компоненту Go
`store-gateway`. Python и TypeScript никогда не держат прямой хендл к базе данных. Все
долгосрочные записи проходят через gRPC-интерфейс `PersistenceService`.

Это разделение является архитектурным исправлением противоречия, присутствовавшего в ранних
предложениях (P1/P2), которые декларировали единое владение базой данных, одновременно позволяя
LangGraph checkpointer писать в тот же файл.

## Краткосрочная память — эпизодическая (в рамках запуска)

### Механизм

Объект LangGraph `RunState` **и есть** рабочая память для запуска. Это типизированный
`TypedDict`, который накапливает наблюдения за страницей, запланированные действия, выполненные
результаты и счётчик подряд идущих неудач восстановления (`consecutive_heal_failures`) на протяжении
всего жизненного цикла запуска. Бюджет токенов — это процесс-глобальный `BudgetTracker`
(`brain/budget.py`), а не поле `RunState`; полей human-gate в `RunState` нет.

`RunState` сохраняется в checkpoint при каждом переходе узла `checkpoint` через LangGraph-
чекпойнтер — синхронный `SqliteSaver` по умолчанию, либо синхронный `PostgresSaver`, если
задана переменная окружения `CHECKPOINT_DSN` (`brain/__main__.py:_checkpointer`) — который
пишет в **отдельный файл/БД** от основной базы данных store-gateway.

### Расположение файлов базы данных

| Контекст | Путь checkpoint DB |
|---------|-------------------|
| Explore / replay запуск | `<artifact_dir>/checkpoint.db` — уникален для `run_id` (`brain/__main__.py:135`) |
| Многоходовый chat (turn-N refine) | `state/conversations.db` — общая и НЕ эфемерная БД, ключ `thread_id=conversation_id`; переопределяется `SENTINEL_CONVERSATIONS_DB`; поток НЕ удаляется по завершении хода (`brain/__main__.py:_conversations_store_path`) |
| Задан `CHECKPOINT_DSN` (любой режим) | Postgres через синхронный `PostgresSaver`, требует одноразового `saver.setup()` — заменяет путь к SQLite-файлу выше |

Это **никогда не тот же файл**, что и основная БД store-gateway (по умолчанию
`state/locators.db` — флаг `-db` у `cmd/store-gateway`, тот же путь константой в
`brain/__main__.py:_STORE_PATH`). LangGraph-чекпойнтер и Go store-gateway являются
независимыми единственными писателями своих соответствующих баз данных. Именно это делает
утверждение «Go store-gateway — единственный писатель основной базы данных» структурно
истинным.

### Ограничение истории обновлений (GAP-M9-20)

`RunState` **не содержит** отдельного `episodic_buffer` — такого поля в состоянии нет.
Реальный механизм ограничения истории (`brain/graph.py:105-141`) работает над
пользовательскими репликами многоходового диалога (`_user_turns`): `_capped_history()`
оставляет последние `SENTINEL_REFINE_HISTORY_KEEP` реплик (по умолчанию 6) без изменений, а
все более старые реплики схлопывает в одну строку через `_rolling_summary()` — чистое
форматирование строки (`"{N} turn(s); started: {текст первой реплики}"`), **без обращения
к LLM**. Это ограничивает рост refine-промпта при длинных многоходовых разговорах, не
теряя количество и содержание самой первой реплики.

### Восстановление после сбоя

Если Python brain падает в процессе запуска:
1. Оркестратор обнаруживает завершение gRPC-потока (в пределах интервала health-ping 5 секунд).
2. Запуск помечается как `FAILED`, частичное состояние записывается через store-gateway.
3. Файл checkpoint DB LangGraph остаётся нетронутым на диске.
4. `agentctl run --resume <run_id>` перезапускает brain, который перезагружает
   `RunState` из checkpoint и продолжает с последней границы узла —
   без потери работы.

## Долгосрочная память — межсессионная (store-gateway)

Долгосрочное состояние принадлежит **исключительно** компоненту Go `store-gateway`.

- **Единственный писатель:** все записи сериализуются через gRPC-интерфейс `PersistenceService`.
  Ни один компонент Python или TypeScript никогда не открывает прямое соединение с БД.
- **Параллельные читатели:** `control-api` и `agentctl` могут читать параллельно
  в режиме SQLite WAL без блокировки писателя.
- **Миграции схемы (реальность на M13):** сегодня — идемпотентный `CREATE TABLE
  IF NOT EXISTS` (+ разовые `ALTER`) в `store-gateway` при старте, для heal/trust-
  таблиц и **6 доменов M13** (runs·scenarios/tests·chats·results·metrics + `config`, ADR-050/062).
  SQL написан портируемо (`ON CONFLICT DO UPDATE`, без SQLite-only-синтаксиса в M13-
  доменах). `golang-migrate` + Postgres-бэкенд (за `STORE_DSN`) — **аспирация,
  отложено в M13-service** (M11/ADR-053); `STORE_DSN` сейчас распознаётся и
  отклоняется (fail-loud), а не молча падает на SQLite.

### Таблицы

#### `healed_locators`

Основной кеш амортизации. Исцелённый локатор сохраняется после успешного исцеления и
повторно используется в последующих запусках до тех пор, пока структурный хеш целевого
поддерева не изменится — после чего он автоматически вытесняется. Реальная схема
(`internal/store/server.go:28-32`):

| Столбец | Тип | Описание |
|--------|------|-------------|
| `page_path` | TEXT | Путь страницы, на которой произошло исцеление |
| `semantic_id` | TEXT | Стабильный семантический идентификатор элемента |
| `strategy` | TEXT | Использованная стратегия исцеления |
| `value` | TEXT | Значение исцелённого локатора |
| `confidence` | REAL | Итоговая оценка уверенности после скидок и проверки в живом DOM |
| `dom_subtree_hash` | TEXT | SHA-256 целевого поддерева на момент исцеления |
| `status` | TEXT | `active` по умолчанию; `deprecated` после автовытеснения (`EvictStale`) |
| `times_used` | INTEGER | Счётчик использований локатора (по умолчанию 0, растёт через `BumpUsed`) |
| `created_at` | REAL | Unix-время (секунды, float) первого сохранения записи |

**Первичный ключ:** `(page_path, semantic_id, dom_subtree_hash)` — не только
`(page_path, semantic_id)`: разные `dom_subtree_hash` для одного элемента сосуществуют как
отдельные строки.

**Амортизация и автовытеснение:** при поиске (`Lookup`) строка ищется по `page_path` +
`semantic_id` + текущему `dom_subtree_hash` и статусу `active`. Совпадение → повторное
использование с нулевыми затратами LLM. Несовпадение → `EvictStale` помечает прежние строки
этого элемента `deprecated`, выполняется свежее исцеление. Это ограничивает инвалидацию
структурным окружением элемента, а не всей страницей — посторонние рекламные объявления,
баннеры или аналитические виджеты не могут инвалидировать все кешированные локаторы.

---

> **Примечание:** отдельной долгосрочной таблицы `page_models` в store-gateway не
> существует — ни в legacy heal/trust-схеме, ни в 6 доменах M13 (`internal/store/server.go`).
> `page_model` — это поле `RunState` (`brain/state.py`), то есть часть краткосрочной
> checkpoint-памяти запуска, а не отдельная запись в долгосрочном хранилище.

#### `golden_snapshots`

Неизменяемые регрессионные базовые линии, ключуемые по странице/шагу (`page_key`). Никогда
не обновляются автоматически при CI-запуске. Реальная схема
(`internal/store/server.go:37-39`):

| Столбец | Тип | Описание |
|--------|------|-------------|
| `page_key` | TEXT | Ключ страницы/шага, к которому относится снимок (primary key) |
| `a11y_hash` | TEXT | SHA-256 нормализованного дерева a11y после завершения шага |
| `screenshot_hash` | TEXT | Перцептивный хеш скриншота после действия |
| `created_at` | REAL | Unix-время (секунды, float) записи |
| `mac` | TEXT | HMAC-SHA256 (#24) от `page_key`+`a11y_hash`+`screenshot_hash`, ключ — `state/golden.key`; защита от подмены строки в обход `SaveGolden` |

**Путь мутации:** `agentctl baseline update --plan <plan.json> [--target <URL>]` —
**единственная** команда, обновляющая базовые линии. Запись — `INSERT OR REPLACE` по
`page_key` (перезаписывает предыдущую строку целиком; таблица не хранит отдельный архив
прежних версий или поле `superseded_by`). В CI-запусках отсутствует кодовый путь, делающий
эту таблицу доступной для записи.

**Проверка целостности:** каждое чтение (`GetGolden`) пересчитывает и сравнивает `mac`;
отсутствующий или неверный MAC отклоняется как `codes.DataLoss` («golden integrity: missing
or invalid MAC … tampered or DB swapped»), что brain транслирует в контролируемый код
завершения вместо того, чтобы тихо довериться подменённой строке.

#### `healing_audit`

Append-only криминалистический журнал каждой попытки исцеления (только `INSERT`, никаких
`UPDATE`/`DELETE`). Реальная схема (`internal/store/server.go:33-36`) — без колонки `mac`
(в отличие от `golden_snapshots`, эта таблица не защищена HMAC):

| Столбец | Тип | Описание |
|--------|------|-------------|
| `run_id` | TEXT | Запуск, в котором произошла попытка |
| `step` | INTEGER | Индекс шага внутри плана |
| `semantic_id` | TEXT | Семантический идентификатор целевого элемента |
| `page_path` | TEXT | Путь страницы, на которой произошла попытка |
| `strategy` | TEXT | Использованная стратегия исцеления |
| `original` | TEXT | Локатор, который не сработал |
| `healed` | TEXT | Кандидат-локатор, выданный стратегией |
| `confidence` | REAL | Итоговая оценка после всех скидок |
| `outcome` | TEXT | Итог попытки (конкретный набор значений определяется вызывающим кодом brain, не БД) |
| `dom_hash` | TEXT | Хеш поддерева на момент попытки исцеления |
| `ts` | REAL | Unix-время (секунды, float) добавления строки |

Эта таблица — источник данных для `agentctl calibrate` и CI-артефакта, вычисляющего
точность/полноту автоматически исцелённых локаторов за скользящее окно.

#### `step_failures`

Трекинг сбоев на уровне шагов для логики карантина нестабильных тестов с учётом AUT-SHA.
Реальная схема (`internal/store/server.go:40-43`):

| Столбец | Тип | Описание |
|--------|------|-------------|
| `plan_id` | TEXT | План, к которому относится шаг |
| `step_key` | TEXT | Составной ключ, идентифицирующий шаг (например, `plan_id:step_id`) |
| `last5` | TEXT | JSON-массив последних до 5 бинарных исходов: `1` = pass, `0` = fail |
| `last_aut_sha` | TEXT | AUT git SHA, записанный при последнем прогоне |
| `quarantined` | INTEGER | `1`, если шаг в карантине, иначе `0` — вычисляется из `last5` при каждом `RecordStep`; отдельного счётчика `fail_count` в схеме нет |

**Первичный ключ:** `(plan_id, step_key)`

**Логика карантина** (`RecordStep`, `internal/store/server.go:334-390`): при смене AUT SHA
`last5` сбрасывается. Шаг помещается в карантин, когда в `last5` набирается **≥3** записи
`0` (fail) из последних до 5. Снимается автоматически при **3 подряд** записях `1` (pass) в
конце `last5` — либо вручную через `agentctl locators clear-quarantine`.

#### `runs`

По одной строке на запуск (M13, ADR-050) — переживает рестарт `control-api`/`agentctl`, в
отличие от прежней in-memory карты запусков. Реальная схема
(`internal/store/server.go:48-51`); RPC `RunRecord` (`proto/store.proto:15-28`) несёт те же
11 колонок плюс read-only `found` (не хранится в БД — признак «запись не найдена» у
`GetRun`):

| Столбец | Тип | Описание |
|--------|------|-------------|
| `run_id` | TEXT | Уникальный идентификатор запуска (primary key) |
| `conversation_id` | TEXT | Join с `chats` (M13) — до этого существовал только в argv и терялся при рестарте |
| `mode` | TEXT | `explore` \| `goal` \| `describe` \| `replay` \| `baseline` \| `chat` |
| `target` | TEXT | URL AUT |
| `planner` | TEXT | Использованный планировщик |
| `state` | TEXT | `running` \| `done` \| `failed` |
| `exit_code` | INTEGER | Код завершения процесса brain |
| `artifact_dir` | TEXT | Путь к каталогу артефактов запуска |
| `error` | TEXT | Текст ошибки, если запуск завершился неудачно |
| `started_at` | TEXT | Время начала запуска (RFC3339) |
| `finished_at` | TEXT | Время завершения (RFC3339; пусто, пока запуск выполняется) |

Подробные результаты шагов/покрытия и метрики токенов — не в `runs`, а в соседних
M13-доменах `results` и `metrics` (`proto/store.proto`), не описанных подробно в этом
документе.

## Обоснование хранилища

### Почему SQLite WAL для основного хранилища

- **Нулевая операционная нагрузка:** нет демона, сетевого порта, кластера — один файл.
  Резервное копирование — это `cp` или `sqlite3 .dump`. Подходит для 1–10 параллельных
  запусков на одном хосте.
- **Модель единственного писателя:** эксклюзивное право записи Go через `store-gateway`
  сериализует все мутации. WAL-режим позволяет неограниченному числу параллельных читателей
  (`control-api`, `agentctl`) работать без блокировки писателя.
- **Переносимость схемы:** схема написана с совместимостью с Postgres. При введении Postgres
  миграция представляет собой смену драйвера в `store-gateway` — без переписывания схемы.

### Почему checkpoint DB отделена

Хранение LangGraph-чекпойнтера (`SqliteSaver`/`PostgresSaver`) в отдельном файле/БД делает
контракт владения однозначным: Go store-gateway — единственный писатель основной базы
данных, Python brain — единственный писатель базы данных checkpoint, TypeScript
`pw-executor` не пишет ни в ту, ни в другую. Два независимых гарантии единственного
писателя, проверяемые инспекцией, а не соглашением.

### Postgres: checkpoint DB vs основная БД store-gateway

Для **checkpoint-БД brain** переключение на Postgres уже реализовано и управляется
оператором вручную через переменную окружения `CHECKPOINT_DSN`
(`brain/__main__.py:_checkpointer`, M5-3): если она задана, brain использует синхронный
LangGraph `PostgresSaver` вместо `SqliteSaver`, с одноразовым вызовом `saver.setup()` при
подключении. Это **не** `AsyncPostgresSaver` — цикл brain синхронный.

Для **основной БД store-gateway** Postgres не реализован: `STORE_DSN` распознаётся и
**явно отклоняется** ошибкой запуска (`internal/store/server.go:96-99`, «the Postgres
backend is deferred to M13-service») вместо тихого отката на SQLite. Переключение драйвера
с `modernc.org/sqlite` на Postgres — задача M13-service (M11/ADR-053); схема уже написана
переносимо для этого перехода.

### GC checkpoint'ов

Отдельной автоматической очистки checkpoint-БД в `store-gateway` **нет**: Go store-gateway
(`internal/store/server.go`) не читает и не удаляет ни `checkpoint.db`, ни
`state/conversations.db` — эти файлы принадлежат исключительно чекпойнтеру Python brain
(LangGraph `SqliteSaver`/`PostgresSaver`), а не store-gateway. Per-run
`<artifact_dir>/checkpoint.db` естественно ограничен временем жизни каталога артефактов
запуска; `state/conversations.db` — общая и не эфемерная БД (см. выше), которая сегодня не
подчищается автоматически. Управление её ростом (архивация/ротация старых
conversation-потоков) — операционная задача, не реализованная в коде store-gateway.
