# Sentinel — Наблюдаемость и управление затратами

> 🌐 **Русский** (основная версия) · [English](OBSERVABILITY.en.md)

Основано на синтезе дизайна от 2026-06-23; канонический итог в ../ARCHITECTURE.md.

> **M13 (2026-07-04):** store-gateway получил `metrics`-домен (time-series-схема + RPC, ADR-050) — сегодня это схема+RPC (наполнение от реального writer'а + native-графики метрик-в-UI = **M15**, ADR-051). Prometheus/Pushgateway-экспорт (ниже) не тронут — остаётся опциональным.

---

## Обзор

Наблюдаемость в Sentinel организована в четыре ортогональных уровня: распределённая трассировка
(добавляется в M4), неизменяемый транскрипт принятых LLM-решений для каждого запуска, контроль
токенового бюджета с graceful degradation и трассировки браузера Playwright. Все четыре являются
первоклассными артефактами, а не доработками постфактум.

---

## 1. Распределённая трассировка (OpenTelemetry)

OTel-спаны вводятся в **M4** — не с первого дня. Это намеренный выбор против
оверинжиниринга: фреймворк стабилизируется до добавления слоя телеметрии.

**Охват:** Каждый узел LangGraph испускает один OTel-спан. Вызовы MCP-инструментов (pw-executor)
и gRPC-вызовы Go являются дочерними спанами охватывающего спана узла, формируя полную
иерархию parent-child для каждого запуска.

**Атрибуты спанов (as-built):** спаны отдельных узлов (`node.<name>`, по одному на узел
LangGraph) **не несут атрибутов** — `_traced()` открывает спан без kwargs
(`brain/graph.py:447-452`). Атрибуты выставляются только на двух видах спанов:

| Спан | Атрибуты | Источник |
|---|---|---|
| `sentinel.run` — chat (`brain/__main__.py:238`) | `run_id`, `mode`, `conversation_id`, `store` | — |
| `sentinel.run` — explore/replay (`brain/__main__.py:509-511`) | `run_id`, `mode`, `transport`, `store` | — |
| `heal.llm` (LLM-вызов в узле heal) | `model`, `prompt_hash`, `llm.prompt_tokens`, `llm.completion_tokens` | `brain/healing.py:129`, `brain/otel.py:53-64` |

`step_index`, `run_mode` (на узел), `latency_ms`, `cost_usd`, `decision_type`, `confidence` —
целевая схема раннего дизайна; в коде не выставляются.

Хранение `prompt_hash` (SHA-256 текста промпта), а не самого промпта, предотвращает появление
секретов, встроенных в состояние страницы, в бэкендах трассировки.

**Распространение контекста:** W3C Trace Context распространяется в gRPC-метаданных
(граница Go↔Python) и в метаданных MCP-вызовов (граница Python↔pw-executor), поэтому
единственный trace ID проходит через все три уровня среды выполнения.

**Путь экспорта:** OTLP → Grafana Alloy → **Tempo** (домашняя лаборатория) / **Jaeger** (dev).

**Семплирование:** 100% для запусков `explore` и `ci`. Каждый запуск должен быть
проверяемым для доверия; головное отбрасывание не применяется.

## 2. Неизменяемый транскрипт LLM

**Расположение:** `/runs/{run_id}/llm-transcript.jsonl`

Каждый вызов LLM дописывает ровно одну JSON-строку. Файл выполняет `fsync` в конце запуска
и **никогда не перезаписывается и не изменяется** после этого момента. Он испускается как
CI-артефакт вместе с `report.json`/`report.html` (`brain/report.py::generate()`).

**Схема записи:**

Реальная запись (`tx_write`, `brain/graph.py:225-245` → `brain/__main__.py:113-115`) — ровно **7 полей**:

| Поле | Тип | Описание |
|---|---|---|
| `step` | int | Номер шага |
| `planner` | string | Планировщик решения (`llm` \| `heuristic`) |
| `model` | string \| null | Идентификатор модели (null для heuristic) |
| `decision` | string | Принятое действие |
| `reason` | string | Обоснование решения |
| `prompt_tokens` | int \| null | Токены промпта |
| `completion_tokens` | int \| null | Токены ответа |

Полей `ts`/`run_id`/`step_id`/`node`/`latency_ms`/`cost_usd`/`decision_summary`/`temperature` в записи **нет**.

**Сценарии использования:** отладка решений в offline-режиме; атрибуция затрат по узлам;
итерация промптов без повторного обращения к API; аудит соответствия («что решил агент и почему»).

## 3. Токеновый бюджет, внутрипроцессный счётчик и жёсткий потолок на стороне Go

Контроль токенового бюджета использует трёхуровневую конструкцию. Каждый уровень независим;
внешний уровень срабатывает даже при сбое внутреннего.

### Уровень 1 — Внутрипроцессный счётчик (Python brain)

Brain поддерживает dict `token_usage` с ключом `model_id → {prompt, completion, cost_usd}`
и dict `token_budget` с ограничениями по моделям. **Перед каждым вызовом LLM** brain
проверяет остаток бюджета. Никаких gRPC-вызовов туда-обратно на каждый вызов LLM не
выполняется — этот антипаттерн оверинжиниринга был отброшен из ранних предложений.

**Лимиты по умолчанию:**

| Бюджет | Модель | По умолчанию |
|---|---|---|
| `plan_token_limit` | Opus 4.8 (по умолчанию) | 50 000 токенов/запуск |
| `heal_token_limit` | Sonnet 4.6 (по умолчанию) | 20 000 токенов/запуск |

> **M6 (ADR-019):** модели в таблице — **дефолты**, маршрутизируются через `LLMBackend`
> (per-role `LLM_BACKEND*`). Токены/стоимость после M6 могут нести идентификатор не-Anthropic
> модели — но это не Prometheus-метка: с M15.1 `model` пишется в `labels_json` метрик-точек
> в SQLite `metrics`-домене store-gateway (`cmd/control-api/main.go:660`), см. §5.

### Уровень 2 — Жёсткий потолок на стороне Go (оркестратор)

Оркестратор Go независимо применяет жёсткий потолок, сверяя счётчик токенов brain, получаемый
в каждом сообщении потока `RunEvent`. Если brain превышает лимит, Go фиксирует превышение и
может завершить дочерний процесс brain. Потолок Go работает **без** gRPC-вызова на каждый
вызов LLM — сверка выполняется с гранулярностью событий.

### Уровень 3 — Graceful degradation (не аварийное завершение)

Исчерпание бюджета **не приводит** к жёсткому прерыванию запуска. Вместо этого:

- **Узел plan:** прекращает генерировать новые действия исследования; текущий план замораживается
  как частичный (plan_hash по-прежнему вычисляется по доступным шагам).
- **Узел heal:** откатывается на детерминированную ротацию стратегий L1–L6 только; вызовы
  модели heal/plan (по умолчанию Sonnet/Opus) не выполняются.

Порог — не 80%, а полное исчерпание лимита: `BudgetTracker.exceeded(role)` возвращает `True`,
когда счётчик роли (или `total_limit`) достигает лимита (`brain/budget.py:63-68`), и вызывающий
узел деградирует, как описано выше. Отдельного события `BUDGET_WARNING` в коде нет — это было
частью раннего дизайна и не реализовано. Фактический расход (`prompt`/`completion`/`total` по
ролям, `summary()`) пишется в отчётные артефакты (`plan.json` / `heal-report.json`); контрол-API
конвертирует его в `cost_usd` (§5) — не в Prometheus.

### Уровень 4 — Надзор, которого до 2026-08-16 не было ни в одной поставке (ADR-126)

Три уровня выше живут **в брейне** и работают всегда. Уровень 4 — модельно-НЕЗАВИСИМАЯ остановка,
та, ради которой ADR-021 и заводил `orchestrator`, — до ADR-126 не работала **нигде**, и это надо
называть прямо: бинарь собирался релизом и ставился в `.deb`, но его не запускал ни один
`docker-compose*.yml`, ни `Dockerfile`, ни `install.sh`, и юнита systemd не существовало. Вместе с
ним были мертвы **перехват и возврат** (ADR-054) и **гейт карты** (ADR-108c): `control-api` отвечал
`"no orchestrator wired"`, а `brain/runcontrol.py::_Noop.wired` был `False`.

Теперь это **долгоживущий сервис**, и разделение труда — весь его дизайн:

* **Оркестратор РЕШАЕТ.** `orchestrator --serve --addr <сокет>` держит по прогону счётчик и объявляет
  превышение. Один сокет на развёртывание, а не один на прогон: `CONTROL_API_ORCH_ADDR` читается
  ОДИН раз при старте control-api, поэтому пер-ран путь `state/sentinel-orch-<id>.sock` нельзя было
  назвать в принципе — отсюда и то, что два параллельных прогона прежняя форма не поддерживала.
* **control-api ИСПОЛНЯЕТ.** Он регистрирует прогон (`StartRun`) СВОИМ идентификатором — тем же,
  что показывает хаб, хранит стор и несёт `Takeover(run_id)`; прежде оркестратор чеканил свой, и
  перехват адресовал бы прогон, о котором тот не слышал. Опрос — `ReportEvent` с **нулевой дельтой**
  (уже существующая идиома: `brain/runcontrol.py::poll()` устроен так же), а на объявленное
  превышение зовётся `cancel.go`.

⚠ **Почему исполняет именно control-api, а не сам оркестратор.** Прежняя страховка была
`cmd.Process.Signal(SIGTERM)` — возможная лишь потому, что процесс был родителем брейна. Сервису это
недоступно **физически**: под compose у каждого сервиса свой PID-неймспейс. Зато у control-api
механизм строго **лучше** прежнего: прогон запущен в своей группе процессов, и сигнал идёт по
ГРУППЕ — SIGTERM, затем SIGKILL, — доставая brain, исполнителя и Chromium там, где прежний доставал
один процесс.

⚠ **Надзор — дополнение, а не предусловие.** Нет оркестратора, недозвон, смерть посреди прогона —
прогон идёт как раньше. Каждая неудача говорится ОДИН раз, а не на каждый опрос: надзиратель,
заливающий журнал строкой каждые две секунды после потери соседа, — это надзиратель, который
выключают.

Включение — два действия, и второе забыть легче первого:

```bash
docker compose up -d                       # сервис orchestrator уже в наборе
# .deb:
sudo systemctl enable --now sentinel-orchestrator
# и обязательно — адрес в /etc/sentinel/control-api.env:
CONTROL_API_ORCH_ADDR=unix:/var/lib/sentinel/orch.sock
```

## 4. Трассировки Playwright

**Источник:** `pw-executor` (наш TypeScript-сервер выполнения Playwright) запускает/останавливает
трассировку для каждого запуска. Один файл `trace.zip` записывается в общую директорию
артефактов, настроенную при запуске сервера.

**Путь передачи:** **brain** сам вычисляет путь трейса (`brain/__main__.py:95`) и передаёт его
`pw-executor` в `browser.traceStop(path=…)` (`:143`); `pw-executor` записывает файл через Playwright
(`pw-executor/src/server.ts:421-428`) и лишь **возвращает** путь обратно — он его не порождает.
gRPC-`RunEvent` поля трейса не несёт, и никакой Go-код `trace.zip` не пишет (только `sweepTraces`
удаляет старые). Отдельного HTTP-сервиса для трейсов больше нет — `cmd/report-service` удалён (ADR-119,
2026-08-09): он собирался и подписывался, но не запускался ничем. `trace.zip` читается напрямую из
директории запуска (или из CI-артефакта), либо отдаётся через артефакт-вайтлист control-api —
`GET /v1/runs/{id}/artifact?name=trace.zip` (token-gated, ADR-099).

**Просмотр:** `playwright show-trace trace.zip`

Никакой пользовательской инфраструктуры трассировки не требуется; встроенный формат трассировки
Playwright (сеть, консоль, снимки DOM, скриншоты, временная шкала действий) является основным
артефактом отладки сбоев CI.

## 5. Метрики Prometheus

Агрегатный скрейп отдаёт **control-api** по корневому `GET /metrics` (ADR-119, `cmd/control-api/metrics_agg.go`).
До 2026-08-09 маршрут числился за `report-service` — бинарём, который собирался и подписывался, но не
запускался НИЧЕМ: отсутствовал в `Dockerfile`, во всех compose-файлах и в `install.sh`. Маршрут
`accessAuthed`: обычный токен видит агрегат по СВОИМ прогонам; машинный токен и развёртывание без
аккаунтов (`owner == ""`) — по всем. Дашборда Grafana и файла правил Alertmanager в репозитории нет.

**Агрегат и per-run артефакт теперь РАЗЛИЧАЮТСЯ.** `<run_dir>/metrics.prom` (`_metrics()` в
`brain/report.py:14-35`) остаётся, как и раньше, чистым node_exporter textfile — без метки, без
`# HELP`/`# TYPE`. Побайтовая конкатенация этих файлов дала бы N дубликатов одной и той же серии
(сломанный скрейп, а не агрегат), поэтому склейка происходит В CONTROL-API при каждом обращении к
`/metrics`: каждая серия получает метку `run="<id>"`, серии группируются по семейству, и на каждое
семейство печатается ровно один `# HELP`/`# TYPE` (тип ВЫВОДИТСЯ из имени — суффикс `_total` ⇒ counter,
иначе gauge). Правка `brain/report.py` не помогла бы сама по себе: на этом репозитории уже 192 каталога
прогонов без run-метки, и переписывать их некому.

| Метрика прогона | Метки | Описание |
|---|---|---|
| `sentinel_run_steps` | `run` | Число шагов в запуске |
| `sentinel_run_exit_code` | `run` | Структурированный exit-код запуска |
| `sentinel_heal_total` | `run` | Количество исцелённых шагов |
| `sentinel_heal_by_strategy_total` | `run`, `strategy` | Количество исцелений по стратегии — `strategy` ∈ ключам `PRIORS` (`testid`, `role_name`, `label`, `text_role`, `css`, `xpath`, `visual`), либо `unknown` (при cache-hit возвращается стратегия закешированного локатора — из `PRIORS`; литерал `cache` меткой не эмитится) |
| `sentinel_regression_total` | `run`, `kind` | Количество регрессий по виду — `kind` ∈ {`a11y`, `visual`} |
| `sentinel_quarantined_total` | `run` | Число шагов в карантине |
| `sentinel_failed_total` | `run` | Число упавших шагов |

Выдача ограничена **500 новейшими прогонами** (`newest first`), а отброшенное ЗАЯВЛЕНО, а не молчит —
три метрики самого агрегатора:

| Метрика агрегатора | Метки | Описание |
|---|---|---|
| `sentinel_metrics_runs_included` | — | Число прогонов, вошедших в этот ответ, после скоупинга по вызывающему |
| `sentinel_metrics_runs_omitted` | `reason` ∈ {`cap`, `unreadable`, `too_large`, `conflict`} | Число отброшенных каталогов прогонов, по причине |
| `sentinel_metrics_lines_dropped` | — | Строк исходного `metrics.prom`, не опознанных как Prometheus textfile-синтаксис |

Обход `runs/` кэшируется на 10 с с single-flight (один диск-walk на N параллельных вызывающих);
нечитаемые каталоги (в этом репозитории есть root-owned от докера) пропускаются и попадают в
`runs_omitted{reason="unreadable"}`, а не роняют запрос 5xx.

**Токены и стоимость по-прежнему не Prometheus-метрика.** С M15.1 они считаются контрол-API
(`cmd/control-api/main.go:666-675`, цена — `costUSD` на `:561`) и пишутся как точки в
`metrics`-домен store-gateway (SQLite, ADR-050/051) с `model` в `labels_json`; UI рендерит их
нативно — не через `/metrics`.

**Скрейп требует credential** — `/metrics` это `accessAuthed`, как и любой другой служебный маршрут
control-api. Рабочий фрагмент `scrape_configs`:

```yaml
scrape_configs:
  - job_name: sentinel
    metrics_path: /metrics
    bearer_token_file: /etc/prometheus/secrets/sentinel-token
    static_configs:
      - targets: ["control-api:8090"]
```

Токен — тот же bearer, что и у остального control-API (`state/control-api.token` в
docker-compose-развёртывании, либо машинный токен в развёртывании с аккаунтами); без него `/metrics`
отвечает **403**, а не 401: отказ гварда всегда `403` (`denyCredential` в
`cmd/control-api/access.go`). Единственный маршрут, отвечающий `401`, — `POST /v1/login` при
неверной паре имя/пароль (`cmd/control-api/session.go`). Маршрут объявлен `accessAuthed` без
`legacyOpen`, поэтому credential нужен и в развёртывании без аккаунтов.

**Отдельный путь (опционально, не изменён этой правкой):** `push_metrics()` (`brain/report.py:70-85`)
пушит 5 gauge-значений в Prometheus Pushgateway на запуск — `sentinel_run_steps`, `sentinel_run_exit_code`,
`sentinel_heal_total`, `sentinel_failed_total` и `sentinel_regression_a11y_total` (имя отличается
от `sentinel_regression_total{kind="a11y"}` в текстовом пути выше — не путать одно с другим).

## 7. Два потока событий и каталог сообщений (ADR-065 · 067 · 068 rev.2)

Разделы 1–6 описывают наблюдаемость **инфраструктурную** — трейсы, метрики, бюджет. Этот раздел про
наблюдаемость **прогона глазами человека**, появившуюся в M9-LIVE.

**Один поглощённый поток stdout+stderr разделяется по АУДИТОРИИ, а не по важности** (`logsink.go`):

| файл | что это | кто читает |
|---|---|---|
| `runs/<id>/logs/events.jsonl` | AG-UI-кадры — **повествование** прогона: «шаг 2 из 40», «клик по кнопке Войти», стратегия починки и её исход | вкладка Live, живой таймлайн |
| `runs/<id>/logs/run.jsonl` | структурированная **диагностика** с уровнем, категорией, модулем, шагом и источником | вкладка Логи |
| `runs/<id>/logs/run.log` | сырой поток 1:1 | человек с `grep`, когда две проекции выше не отвечают на вопрос |

Почему это не одна «правильная» проекция: AG-UI-кадры составляют **82% вывода прогона** и не являются
шумом — они несут историю. Присвоить истории уровень логирования значит её уничтожить, поэтому у неё
свой файл и своя вкладка, а диагностика перестаёт быть на 82% протоколом. Кадры при этом остаются в
кольцевом буфере в памяти — подписка WS `/v1/stream` проигрывает его, чтобы вести живой таймлайн; сток
это **второй** потребитель тех же строк, что и удерживает разделение от вмешательства в живой путь.

**Записи немедленные.** Схлопывание повторов и вложение стек-фреймов — задачи ПОКАЗА и живут на
стороне чтения (`handleRunLogs`), не записи. Первая версия держала запись, чтобы посчитать повторы, и
живой прогон опроверг это дважды: застрявший прогон не печатает ничего нового, поэтому удержанная
запись не попадала в файл ровно столько, сколько длился цикл — тот самый случай, для которого
схлопывание и существует. Плюс реальные повторы приходят с интервалом ~5 с, и любой дедлайн, короткий
достаточно, чтобы держать цикл видимым, был слишком коротким, чтобы что-то схлопнуть.

**Каталог сообщений** (`brain/events.json`) — единственный источник истины для каждой обращённой к
человеку строки. По проводу едет `code`, текст берётся из каталога, а значения подстановок
восстанавливаются обратным сопоставлением английского шаблона с отрендеренной сервером строкой. Оси:

- **уровень** — debug/info/warn/error;
- **категория** — run · plan · heal · hitl · llm · record · system · browser · app · test;
- **источник** выведен из категории (`brain/embed.go::SourceOf`): инструмент · приложение · тестирование;
- **аудитория** (ADR-068 rev.2) — слой над источниками: `business` (приложение+тестирование) против
  `tool`; гейт требует, чтобы аудитории разбивали источники **точно**;
- **`degrades: true`** (34 кода) — единственный законный переход из диагностики в повествование: прогон,
  вышедший с нулём при отсутствующей LLM, обязан сказать это на вердикте, а не спрятаться в логе;
- **вина** (`fault`, ADR-113) — ЧЬЯ это проблема: `none` · `app` · `tool` · `test` · `config`. Ось несут
  только коды, способные ЗАВЕРШИТЬ прогон, и правило это выведено, а не перечислено: запись, объявившая
  `exit`, по определению завершает прогон, значит она же обязана сказать чья вина. Ось намеренно
  ортогональна вердикту — `problem` остаётся ИСХОДОМ, а «чья вина» отвечается отдельно, иначе слов
  понадобилось бы по одному на каждую пару (исход × домен). Запись с `fault` помечает им и саму строку
  `run.jsonl`, поэтому файл остаётся самоописательным для того, кто читает его потом грепом.

**Почему ось понадобилась.** Слово вердикта склеивало три разных конца в один: `exit 1` («шаг не
прошёл» — факт о приложении), `exit 4` («наш код бросил», ADR-087) и `exit -1` («нас убили сигналом»)
приходили к читателю как `problem`, то есть как приглашение чинить своё приложение. Хуже того, HEALTH-001
отдал под отказ в старте `exit 3`, который уже значил `integrity`, — и прогон, отказавшийся из-за
недоступной модели, показывал «несовпадение plan_hash/golden», хотя ни плана, ни эталона там не было.
Точный ответ знает не exit-код, а код, ЗАКОНЧИВШИЙ прогон, поэтому решение принимается из него
(`cmd/control-api/fault.go`), а `exit_codes[N].fault` — лишь запасной для прогона, чей лог не прочитать.

Гейт `tests/test_event_catalog_offline.py` держит это двусторонне: каждый код, который эмитит модуль,
существует в каталоге и называет этот модуль; каждая запись каталога называет модули, которые её
действительно эмитят. Привязка **по модулю, а не по строке** — построчная устарела вся разом при первой
же конверсии.

**Чего здесь нет.** События приложения (`app.*`, семь кодов) доходят до `run.jsonl` и не доходят до
вердикта — прогон может отдать `exit 0` при сыплющем исключениями приложении. Это `GAP-PROD-001`, разбор
в `docs/REGRESSION_MAP.md` §6. Редактирования на стороне записи для чужого вывода тоже нет —
`GAP-SEC-005`, `docs/THREAT_MODEL.md` §4.12.

## 8. Три потока журналов и чего в них нет (HEALTH-005 · ADR-116)

Раздел 7 — про наблюдаемость ПРОГОНА. Этот про наблюдаемость **самого инструмента**: что он делал,
когда и по чьей команде. Замер, обосновавший раздел: до HEALTH-005 сервисный план не логировался
нигде — `session.go` и `configfile.go` имели НОЛЬ строк логирования обоих видов, поэтому создание
аккаунта, смена пароля, удаление аккаунта и правка глобального конфига были бесследны.

| поток | где живёт | что несёт | чем читается |
|---|---|---|---|
| **прогон** | `runs/<id>/logs/run.jsonl` | диагностика ОДНОГО прогона (раздел 7) | вкладка «Логи» · `GET /v1/runs/{id}/logs` · `agentctl logs` |
| **сервис** | `state/logs/service.jsonl` | что делал инструмент: входы и НЕУДАЧНЫЕ входы, аккаунты, правка настроек, отказы в доступе, старт и остановка сервисов | вкладка «Журнал сервиса» · `GET /v1/service-log` · `agentctl service-log` |
| **чужие сервисы** | журнал докера | вывод `ollama`, `litellm`, `webui` — программ, которые не наши | `docker compose logs <сервис>` |

**Почему сервисный поток — файл, а не таблица стора.** `s.store == nil` это поддерживаемый тир
(ADR-075), и аудит, отсутствующий там, где чаще всего работают одиночки, — не аудит. Плюс упавший
стор не должен ронять запись о том, что он упал.

**Один файл на все сервисы, различает поле `svc`.** Пишут четверо: `control-api`, `agentctl`
(`service.log_purged` и `service.vnc_password_source`), `browser` и — с LIVE-VNC — `browser-vnc`.
⚠ Последние два запускают ОДИН И ТОТ ЖЕ бинарь, и различает их только `SENTINEL_SVC_NAME`: без
этой переменной оба писали бы `svc: "browser"`, и поле перестало бы отвечать на вопрос, ради
которого существует. Четыре файла означали бы отвечать на «что было в 14:32» ручным
слиянием.

**Уровни снимают объём, а не отбор** (директива: писать всё и иметь уровни). Чтения `debug`, мутации
`info`, отказ и обращение к чужой строке `warn`, 5xx `error`; по умолчанию `info`. Фильтр стоит на
ЗАПИСИ, потому что журнал, чей шум гасится только фильтром чтения, всё равно платит за него диском.

**Ротация.** `state/logs/service.jsonl` плюс одно предыдущее поколение `.1`; порог
`SENTINEL_SERVICE_LOG_MAX_MB` (16 по умолчанию). У сервисов композа с PR-C стоит `logging:` с
`max-size: 10m` и `max-file: 3` — до него драйвер не был настроен вовсе, то есть ротации не было и
логи умирали вместе с контейнером.

### Чего в этих потоках НЕТ — заявлено, а не умолчано

- **Значений конфигурации.** `service.config_changed` пишет, КАКИЕ СЕКЦИИ изменились, и не пишет
  значения: они несут эндпоинты, бюджеты и пути, и журнал стал бы вторым экземпляром конфигурации без
  той защиты, что есть у первого.
- **Паролей и тел запросов.** Неудачный вход пишет имя, которое ПЫТАЛИСЬ, и никогда пароль. Тела
  запросов и ответов не пишутся вовсе.
- **Содержимого удалённого.** `agentctl purge-service` печатает счётчики и никогда содержимое; та же
  поза, что у `redact-trace` (ADR-098) и `purge-store` (ADR-100).
- **Записей сервиса браузера, легших в окно чистки.** Он пишет из Node, а `flock` там недоступен без
  нативного модуля, которого проект не берёт. Перезапись при чистке дочитывает хвост, дописанный с
  момента снимка, поэтому окно сведено к одному сисколлу — но оно не ноль. Go-писатели блокировку
  берут и не теряют ничего.
- **Структуры у чужих сервисов.** `ollama`, `litellm` и `webui` пишут своим форматом, и мы его НЕ
  парсим: разобрать чужой вывод в структуру, которой у него нет, — это придумать данные. Им
  докеровская ротация и `docker compose logs`; граница проходит здесь и объявлена намеренно.
- **Кто что видит.** Обычный аккаунт видит события, где владелец он; события без владельца — старт
  сервиса, глобальный конфиг, отказ стора — видны только админу или машинному токену. Частичный вид
  НАЗЫВАЕТ себя частичным (`scoped` и `scope_reason` в ответе), потому что «нет записей» и «не ваши
  записи» — разные ответы, и пустой список их не различает.

## 9. Живой вид: про ПРОГОН, а не про сервис (LIVE-PER-RUN, ADR-121)

Разделы 1–8 не различали двух прогонов, идущих в одном браузере: `/live/status`, `/live/frame.jpg` и
`/live/mjpeg` (ADR-111) отвечали про **сервис** — про ту страницу, что оказалась открыта последней.
При двух прогонах сразу это значило: зритель первого видит второй. Показ чужого прогона хуже
отсутствия картинки — отсутствие видно, а неверная картинка неотличима от верной.

**Маршруты принимают `run_id`, и это ОПЦИОНАЛЬНО.**

| Маршрут | CLI | Без `run_id` | С `run_id` |
|---|---|---|---|
| `GET /v1/live/status` | `agentctl live status [--run-id <id>]` | отвечает про новейшую открытую страницу, `scoped:false` | отвечает про страницу этого прогона или называет причину отказа, `scoped:true` |
| `GET /v1/live/frame.jpg` | `agentctl live frame [--run-id <id>]` | то же, плюс заголовки кадра (ниже) | то же |
| `GET /v1/live/mjpeg` | `agentctl live stream [--run-id <id>]` | то же | то же |

Неназванный запрос — то, что шлют `agentctl live frame` без флага и весь код, существовавший до
ADR-121, — остаётся легальным: он не отклоняется, а отвечает про новейшую страницу, как раньше.
Разница в том, что ответ теперь **говорит это явно** — полем `scoped:false` в JSON `/live/status` и
заголовками `X-Sentinel-Run`/`X-Sentinel-Scoped` на самом кадре (JPEG не может сказать это телом).
До ADR-121 «это самая свежая страница» и «это ваш прогон» были неразличимы по ответу.

**Заявка (`POST /live/claim`).** Исполнитель (`pw-executor/src/server.ts::claimLivePage`), как только
у него появляется страница, читает её Chromium `targetId` (`Target.getTargetInfo`) и объявляет его
сервису браузера: `{run_id, target_id}`. Это работает и когда исполнитель НЕ владеет страницей
(режим CDP-attach, ADR-037): `targetId` — единственный идентификатор, который CDP отдаёт одинаково
и владельцу, и клиенту, лишь усыновившему чужую страницу — это установлено прямым замером, а не
предположением, до того как код был написан. Страница НЕ метится по порядку появления, URL или
времени создания — все три ломаются ровно тогда, когда прогонов два.

Заявка **fail-open**: неудача (сервис недоступен, `targetId` не удалось получить, таймаут) не роняет
прогон — наблюдение не вправе убивать работу. Но и не молчит: причина логируется на стороне
исполнителя (`log('live claim failed …')`).

Адрес заявки **выводится** из `PW_CDP_ENDPOINT`, который уже задан control-api в compose (порт
CDP-релея заменяется на `CDP_LIVE_PORT`, путь — на `/live/claim`; вывод объявляется в логе строкой
`live claim endpoint derived from PW_CDP_ENDPOINT: …`), и переопределяется явным `PW_LIVE_CLAIM`.
Второй адрес в compose не заведён — это отдельное решение, а не упущение: `docker-compose.yml`
менять не пришлось, а второй адрес был бы вторым способом разойтись, ровно как это уже случилось
однажды с ключом слияния YAML, съевшим блок `environment:` целиком.

**Отказ вместо подмены.** Именованный прогон, который не разрешается, получает `503` с телом-причиной
(не JSON) — три случая различены, а не свёрнуты в один общий «нет картинки»:

| Причина | Когда |
|---|---|
| «run \<id\> has not claimed a page — …» | прогон ещё не заявлял страницу (не стартовал браузер, либо развёртывание вообще без сервиса браузера) |
| «run \<id\> claimed a page that is no longer open — …» | заявка была, но страница закрыта (прогон завершился) |
| «the browser has no page yet — start a run first» | (только для неназванного запроса) в браузере нет вообще ни одной страницы |
| «run \<id\> shares one browser page with …» | ⚠ **рассинхрон версий, а не обычная работа.** Два прогона заявили ОДНУ страницу. До ADR-128 это была топология (исполнитель усыновлял `pages()[0]`, и второй прогон вёл ту же вкладку); теперь прогон открывает свою, поэтому единственный оставшийся способ сюда попасть — исполнитель старше ADR-128 против нового сервиса браузера. Отказ так и сформулирован, а сам случай пишется в журнал сервиса кодом `service.live_claim_conflict` |

Заявка переживает свою страницу на `CDP_LIVE_PORT`-сервисе `CLAIM_TTL_MS` (по умолчанию 12 часов) —
это то, что делает «прогон закончился, страница закрыта» отличимым от «прогон никогда не заявлял
страницу»: заявка не исчезает в момент закрытия страницы.

**ADR-128: у каждого прогона своя страница.** Раздел выше описывает механизм, который заводился, когда прогоны делили одну вкладку: в режиме CDP-attach исполнитель усыновлял `pages()[0]`, поэтому два одновременных прогона заявляли ОДИН `targetId` (замерено живьём: оба `84DC6185`) и `resolve` честно отказывал ОБОИМ — картинку нельзя отнести к одному из двух. Теперь прогон открывает свою страницу (`context.newPage()`) в том же усыновлённом контексте: сессия пользователя переиспользуется, его открытая вкладка — нет. Замерено после правки: два прогона на разных фикстурах дают разные `url` в `/live/status` и кадры, различающиеся побайтово (9 882 и 10 105 байт), каждый со своим `X-Sentinel-Run`. Всё устройство заявок — `targetId`, `SENTINEL_RUN_ID`, `liveTargetURL`, `scoped:false` для неназванного запроса — остаётся ровно тем же; изменилось только то, что случай «два прогона» перестал быть предметом отказа и стал обычной работой.

⚠ **Прогон закрывает свои страницы, и это видно отсюда.** Свою и попапы, которые она открыла, — на любом пути выхода, включая убийство сигналом. Поэтому после конца прогона `?run_id=` отвечает второй строкой таблицы выше («страница закрыта») вместо картинки соседней вкладки, и это не новая причина, а та же самая, ставшая обычной. ⚠ Своя СТРАНИЦА не делает возможной запись видео над CDP: `recordVideo` — свойство КОНТЕКСТА в момент создания, а контекст остаётся усыновлённым, поэтому отказ ADR-125 у двери в силе.

**`/live/status` несёт три новых поля**, не переименовывая старые (`streaming`/`has_page`/`url`/
`last_frame_ts`/`ack_errors`/`error` не тронуты):

| поле | значение |
|---|---|
| `run_id` | эхо запрошенного `run_id`, либо `null` |
| `scoped` | `true`, если ответ про заявленную страницу ИМЕННО этого прогона; `false` — про новейшую страницу вообще |
| `reason` | причина отказа (см. таблицу выше), либо `null` |

**`SENTINEL_RUN_ID`.** До ADR-121 `agentctl run` порождал свежий случайный `runID`, никак не связанный
с тем именем, под которым control-api уже создал каталог прогона (`runs/control-<id>` при
`spawnRun`), — заявка ушла бы под ЧУЖИМ именем, и хаб, спрашивающий про `<id>` control-api, никогда
бы её не встретил. `cmd/control-api/main.go::spawnRun` передаёт дочернему процессу
`SENTINEL_RUN_ID=<id>`; `cmd/agentctl/main.go::cmdRun` использует его вместо свежего `runID`, если он
задан. Имя переменной намеренно НЕ `RUN_ID` — частое имя окружения, случайное наследование которого
дало бы двум несвязанным прогонам одну и ту же заявленную личность.

**Единая сборка адреса в control-api.** `cmd/control-api/live.go::liveTargetURL` — одна функция на оба
проксирующих обработчика (`handleLiveStatus`, `proxyLive`). До неё они строили URL к сервису браузера
раздельно, и это разошлось незамеченным: `?run_id=` добавлялся к запросу `proxyLive`, но терялся в
`handleLiveStatus` — ничего не падало, `/live/status` просто отвечал про другую страницу, чем
`/live/frame.jpg`. Только `run_id` пробрасывается дальше — не весь query string, чтобы этот прокси не
стал способом передать сервису браузера произвольные параметры.

**Заголовки кадра.** `GET /v1/live/frame.jpg` и `GET /v1/live/mjpeg` несут `X-Sentinel-Run` (эхо
запрошенного `run_id`, пусто для неназванного запроса) и `X-Sentinel-Scoped` (`"true"`/`"false"`) —
control-api пробрасывает их из ответа сервиса браузера (`proxyLive`). Это единственный способ узнать
принадлежность кадра НЕ читая JSON: тело — чистый JPEG или multipart-поток.

## 10. Выбор режима наблюдения (LIVE-MATRIX, ADR-120)

Разделы 1–9 описывали инфраструктурную наблюдаемость и живой вид одного сервиса. Этот раздел —
про то, СКОЛЬКО прогон показывает и кому, и это ПОЛЬЗОВАТЕЛЬСКИЙ выбор, а не выведенное состояние.

До ADR-120 наблюдением управляли четыре несвязанных переключателя, читаемых в четырёх местах трёх
процессов на двух языках — `PW_HEADED`/`PW_HEADLESS` (`pw-executor/src/launch.ts:26`),
`SENTINEL_TRACE_SCREENSHOTS` (`pw-executor/src/server.ts:489`), `SENTINEL_LIVE_FRAMES`
(`brain/graph.py:45`), `PW_NO_TRACE` (не режим — см. ниже), — и ни одно место не знало всех
четырёх. Хуже: ОДНА и та же картинка — кадр на шаг — гейтилась ДВУМЯ переменными в ДВУХ языках,
поэтому выключение одной давало наполовину наблюдаемый прогон, молчащий о пропавшей половине.
Резолвер `brain/observe.py` (`resolve()`/`apply()`) сводит выбор в одно место и пишет обе кадровые
переменные ВМЕСТЕ — это единственный писатель (гейт держит это обходом всего `brain/`). Тем же
раскрытием, и по той же причине, едет третья — `SENTINEL_DECORATE` (LIVE-HUMAN): не потому, что она
третий кадровый рубильник, а потому, что у одного решения не должно быть второго автора.

### Пять режимов и их цена

| Режим | Что снимается | Цена |
|---|---|---|
| `off` | ничего | быстрее всего; смотреть будет не на что |
| `frames` (дефолт) | кадр на каждый шаг, рендерит хаб | замедляет прогон незначительно |
| `stream` | `frames` + живой скринкаст без украшений | годится и человеку «как есть», и техническим средствам |
| `human` | `stream` + синтетический курсор + `slowMo` + подсветка | **МЕНЯЕТ ТАЙМИНГ** — не для проверки откликов, гонок, таймаутов; не смешивается с голден-режимом |
| `record` ⚠ пока отклоняется | видеофайл артефактом после прогона | на живой вид не влияет |

Текст цены живёт в ОДНОМ месте — `brain/observe.py::COST` (ru+en на режим) — и оттуда же попадает в
схему control-api (`cost` в поле `observe`), откуда его читает форма хаба. Хардкодить цену во
второй раз означало бы завести второй экземпляр, которому предстоит разойтись с первым.

### Где выбирается — три поверхности, одно имя

1. **Настройки развёртывания** — дефолт (`frames`), объявленный в схеме
   (`cmd/control-api/main.go`, поле `observe.default`), а не подразумеваемый молча.
2. **Форма прогона хаба** (`docs/index.html`, селектор `b-observe`) — заполняется из
   `GET /v1/config-schema` (`lvFillObserve`); первый пункт списка НАЗЫВАЕТ унаследованный дефолт, а
   не оставляет поле пустым без объяснения; при выборе режима показывается его цена (блок
   `b-observe-cost`).
3. **`agentctl run --observe off|frames|stream|human|record`** — то же имя, то же множество
   значений, с терминала.

Пустое значение — это НЕ `off`, это «решение не заявлено», и резолвер (`brain/observe.py::resolve()`)
раскрывает его в `DEFAULT`, называя это в логе (`run.observation`, `why` содержит "by default,
nothing was asked for"). Так «я не выбирал» и «я выбрал именно `frames`» остаются разными фактами,
а не одним и тем же действием.

### `human` — поставлен (LIVE-HUMAN)

Режим был ОБЪЯВЛЕН и отклонялся с названной задачей; LIVE-HUMAN принёс машинерию, и `human` вышел из
`NOT_YET` ТЕМ ЖЕ изменением, что и переключатель, который его исполняет. Порознь эти две половины —
ровно то состояние, ради устранения которого отказ и существовал: резолвер, который решает,
переменная, которую никто не экспортирует, и исполнитель, читающий то, чего никто не ставит.

Один переключатель, два конца и ни одного лишнего:

* **`SENTINEL_DECORATE`** = `1`/`0`. Пишет его ТОЛЬКО `brain/observe.py::apply()` — из
  `plan.decorations`, тем же `setdefault`-приёмом, что и два кадровых рубильника, и он же попадает в
  `overrides()`, поэтому выставленный руками переключатель ПЕРЕЖИВАЕТ резолвер и НАЗЫВАЕТСЯ в той же
  строке лога. Читает его ТОЛЬКО `pw-executor`.
* Украшения — часть ПОЛЬЗОВАТЕЛЬСКОГО режима, а не выводимого состояния: `decorations` истинны для
  `human` и ложны для всего остального, и ничто внутри прогона не может включить их само.
* По кадрам `human` ведёт себя как `stream`: живой скринкаст этим планом не гейтится вовсе (его
  включает сам исполнитель), поэтому «как stream» здесь означает ровно «кадры остаются включёнными»,
  что и даёт `mode != off`. Отдельного случая для `human` на кадровой оси нет — и не должно
  появиться, пока скринкаст не станет переключателем этого резолвера; тогда `stream` и `human`
  получат его ВМЕСТЕ, одной строкой.

**Кадр для МОДЕЛИ и для ГОЛДЕНА обязан быть ЧИСТЫМ.** Оверлей снимается ВОКРУГ такой съёмки, а не
отменяется целиком: человеку курсор виден всегда, а картинка, которую читает модель или с которой
сверяется эталон, не содержит нарисованного нами. Иначе украшение попадало бы во вход, по которому
принимают решение, — и «UI изменился» стало бы неотличимо от «мы дорисовали курсор».

`human` по-прежнему отклоняется при голден-прогоне (`baseline=True`), и это отказ ДО старта:
замедление и оверлей не ухудшают эталон, они делают его НЕВЕРНЫМ, и это вскрывается только позже, на
чужом прогоне. Эталон снимают в `frames`, а смотрят на него потом в `human`.

### `record` — поставлен (LIVE-RECORD, ADR-125), и `NOT_YET` опустел

`record` вышел из `NOT_YET` тем же изменением, что и `SENTINEL_RECORD`, — ровно как `human` до него.
**Множество отказов теперь пусто: каждый режим, который продукт объявляет, он исполняет.** Пустое
`NOT_YET` — это состояние, а не забытый список, и гейт `tests/test_observation_modes_offline.py` был
переписан ПОД него осознанно: пол «есть хотя бы один неотстроенный режим» заменён на утверждение
«каждый объявленный режим ПРОИЗВОДИТ план».

Что делает режим:

* **`SENTINEL_RECORD`** = `1`/`0`, четвёртый рубильник набора. Пишет его ТОЛЬКО
  `brain/observe.py::apply()` из `plan.video`, читает ТОЛЬКО `pw-executor` (`src/record.ts`).
* `recordVideo` ставится на НАШ `newContext`, размер прикреплён к детерминистическому вьюпорту:
  запись окна другого размера показывала бы раскладку, которой прогон не видел.
* Артефакт — `runs/<id>/video.webm`, достаётся тем же маршрутом, что и все остальные
  (`GET /v1/runs/{id}/artifact?name=video.webm`), и проигрывается прямо в панели артефактов хаба.

**Запись идёт С КУРСОРОМ** — требование Alex 2026-08-02: без него она так же нечитаема, как голый
скринкаст. Значит `record` рисует в страницу, а рисование — это `slowMo` и оверлей, то есть ВСЕ
последствия `human`: **тайминг изменён, эталоном такой прогон быть не может**. Оба факта выведены из
одного кортежа `observe.DECORATED`, чтобы их нельзя было выставить порознь; голден-отказ ходит по тому
же кортежу и подхватил `record` без отдельной строки. Кадр для модели и для голдена остаётся ЧИСТЫМ —
механизм «опустить оверлей вокруг съёмки и вернуть» построен ADR-120 и переиспользован как есть.

⚠ **Над CDP-attach режим НЕВОЗМОЖЕН, и это отказ, а не деградация.** `recordVideo` — свойство
контекста в момент СОЗДАНИЯ, а в CDP-attach контекст усыновлён. У `slowMo` та же форма проблемы, и он
ДЕГРАДИРУЕТ: исполнитель доплачивает пацинг своей паузой. У видео доплатить нечем — прогон просто
кончится без файла, а прогон, не сделавший единственного, о чём его просили, не является «слегка
ухудшенным». Поэтому сочетание отклоняется ДО старта (`exit 3`, `fatal.observe_refused`, причина
называет CDP), а на стороне исполнителя стоит второй, громкий страж `videoUnavailable` — на случай,
если переключатель придёт другим путём. Пустая строка в `PW_CDP_ENDPOINT` подключением НЕ считается:
так compose пишет «не настроено», и отказывать на этом означало бы отказ, с которым нечего делать.

⚠ **Решение писать принимается НА СТАРТЕ — и это цена, а не деталь.** ADR-084 решает про трейс в
КОНЦЕ, поэтому байты зелёного прогона не касаются диска вовсе. Здесь так нельзя: файл пишется по ходу,
и остаётся только удаление постфактум. По решению Alex запись **удаляется на зелёном**, а
`SENTINEL_VIDEO_ALWAYS=1` оставляет её всегда. Отказ ОБЪЯВЛЯЕТСЯ вместе с именем этого рычага: человек,
попросивший записать прошедший прогон, иначе прочтёт пустоту как поломку режима.

Сборщик `collect-live-run.sh` видео **не забирает** и флага `--with-video` не имеет. Причина та же,
что у трейса: пиксели не редактируются. Структурная и текстовая очистка умеет обнулить `value` в шаге
и замаскировать токен в строке лога и не умеет ничего сделать с записью, на которой заполненная форма
входа была на экране столько, сколько была.

### Прогон, снятый ДЛЯ ЧЕЛОВЕКА, помечен там, где смотрят его результат

Цена режима напечатана рядом с выбором — но выбор делают один раз, а результат читают неделю спустя.
Прогон, выполненный в `human`, несёт пометку там, где смотрят его итог: в карточке вердикта сразу
после прогона и закреплённой строкой в виде «Логи» — «⚠ Прогон снят для ЧЕЛОВЕКА, режим наблюдения
`human`; курсор, замедление и подсветка МЕНЯЮТ ТАЙМИНГ: откликам, гонкам и таймаутам этого прогона
верить нельзя, и эталоном он быть не может».

Источник у пометки ОДИН — событие `run.observation`, которое брейн печатает ДО старта и которое несёт
и режим, и `decorations`. Живьём оно приезжает строкой лога, после прогона лежит в
`runs/control-<id>/logs/run.jsonl` и отдаётся `GET /v1/runs/{id}/logs?code=run.observation` — поэтому
ответ на «чем это снято» переживает и вкладку, и перезапуск control-API. Второго поля, второго
артефакта и отдельного флага нет намеренно: две записи об одном факте расходятся, и тогда ни одной
верить нельзя. Значения достаются из строки ШАБЛОНОМ КАТАЛОГА (тем же механизмом, которым вид «Логи»
показывает русский текст с настоящими значениями), а не своей регуляркой, которая разошлась бы с
каталогом при первой же правке текста события.

### `PW_NO_TRACE` — это не режим

`PW_NO_TRACE` не входит в перечисление и никогда не пишется резолвером наблюдения. Это
предохранитель ввода СЕКРЕТА с двумя независимыми точками отказа: `pw-executor/src/server.ts:610`
бросает при попытке ввести секрет, пока трейс активен, и `brain/__main__.py` даёт exit 3, если
секрет добрался бы до трейса (`fatal.secret_would_leak_to_trace`). Режим `off`, который бы его
снимал, молча убрал бы эту защиту; режим, который бы его ставил, сломал бы каждый login-as-test
прогон. Обе стороны неверны, поэтому `PW_NO_TRACE` держится отдельно от выбора наблюдения и не
показывается в интерфейсе рядом с ним.

### Слой VLM: не режим, а следствие

Модель, способная читать кадры (vision-heal), не решает, снимать ли их — это решение человека. Но
когда `heal_llm` и vision настроены (`LLM_VISION`/`LLM_VISION_HEAL`), а наблюдение выключено
(`observe=off`), резолвер добавляет строку в `why`: «vision heal is configured but observe=off, so
it will receive no frame and cannot look at anything». Без этой строки самопочинка, которой нечего
чинить (нет кадра), неотличима от самопочинки, которая молча не сработала, — а это ровно тот класс
тишины, который LIVE-MATRIX устраняет.

### Проверено

Гейт `tests/test_observation_modes_offline.py` держит: оба гейта кадров пишутся ВМЕСТЕ и только
резолвером; `PW_NO_TRACE` этим файлом не пишется, а предохранитель жив на обеих сторонах; схема
control-api, флаг CLI и множество резолвера согласны и на перечислении режимов, и на списке «не в
этой сборке» (иначе хаб обещал бы обратное тому, что прогон делает); отказ резолвится ДО спавна
исполнителя; украшения истинны ТОЛЬКО для `human`; перечень переключателей ВЫВЕДЕН — что пишет
`apply()`, то и называет `overrides()`, с полом на число.

Гейт `tests/test_live_human_mode_offline.py` (LIVE-HUMAN) проверяет то, чего резолвер о себе сказать
не может: он гоняет ОТГРУЖЕННУЮ точку входа `python -m brain` с исполнителем-заглушкой, который
выписывает собственное окружение, и читает, что ребёнок ПОЛУЧИЛ. `observe=human` → `SENTINEL_DECORATE=1`
у ребёнка; любой другой режим → `0`; `human` + голден → `exit 3` и заглушка не запускалась ВОВСЕ;
режим и `decorations` достаются обратно из строки `run.observation` шаблоном каталога. Мутации:
`decorations` зашит в `False`, переключатель убран из `SWITCHES`, `overrides()` скрывает его,
`human` возвращён в `NOT_YET`, схема снова помечает `human` как «не в этой сборке», событие
перестаёт нести `decorations` — все шесть КОМПИЛИРОВАЛИСЬ и все шесть покраснели.

Интерфейс проверен живьём, в headless-Chromium на отгруженной странице: при выборе `human` форма
печатает «⚠ МЕНЯЕТ ТАЙМИНГ …» (кадр снят и просмотрен), опция больше не подписана «не в этой
сборке», а вид «Логи» прогона с `decorations True` показывает закреплённую пометку — и не показывает
её для обычного прогона. Те же две проверки добавлены в DOM-гейт `scripts/hub-dom-check.mjs`; две
мутации страницы (читатель никогда не видит украшений; вид «Логи» не наполняет закреплённое место)
покраснели.
