## Scope

pw-executor gains two browser launch modes from the §F evolution (own-headless → headed → CDP-attach → co-pilot):

- **F2 — headed (visible):** `chromium.launch({ headless: false })` — the user watches the run.
- **F3 — CDP-attach:** `chromium.connectOverCDP(endpoint)` — Sentinel drives the user's **existing** Chrome (started with `--remote-debugging-port`), reusing their session.

**Out of scope:** F4 co-pilot takeover/return — a separate milestone **M9.8** (after the chat UI). No new RPC tools — modes are env toggles (like `PW_NO_TRACE` / `PW_IGNORE_HTTPS_ERRORS`). Engine is **Chromium-only** (ADR-036).

## Contract (what is implemented)

> ⚠ **AMENDED BY ADR-128 (2026-08-18).** What follows is the acceptance record of milestone M9.6 and stays a record of what was accepted THEN. One statement has since changed deliberately: in CDP-attach only the **context** is adopted (session, cookies, login) and the run **opens its own page** (`context.newPage()`), closing it afterwards on every exit path. The user's browser is still never closed, and their tabs are neither read nor driven. The reason: two concurrent runs drove one tab and announced one `targetId`, so the live view refused both. The current description is the ADR-128 row in `ARCHITECTURE.en.md`.

### Mode resolver (`pw-executor/src/launch.ts`)
- Pure function `resolveLaunchPlan(env) → { kind:'launch'|'cdp', headless, cdpEndpoint? }`.
- **Precedence:** `PW_CDP_ENDPOINT` (CDP-attach) > headed (`PW_HEADLESS=0` or `PW_HEADED=1`) > headless (default). Blank/other `PW_HEADLESS` → headless (fail-safe to the deterministic mode).
- Unit test `launch.test.ts` (`node --test`, **no browser**) — 5 cases cover precedence and fallback.

### `ensureBrowser` (`server.ts`)
- **launch branch** (headless/headed): `chromium.launch({ headless })` + our `newContext` with fixed viewport 1280×720 / DSR=1 (determinism, GAP-RISK-009) + `storageState`/`ignoreHTTPSErrors` as before.
- **cdp branch:** `chromium.connectOverCDP(endpoint)`; context = the user's **existing** one (`browser.contexts()[0]`, else `newContext`); our viewport/DSR/`storageState` are **not** applied (it's the user's session); `STORAGE_STATE` is ignored (logged). ⚠ **Amended by ADR-128:** the page is ours (`context.newPage()`); the user's tab is not adopted.
- **Common to both:** traceparent route (if OTLP set, M9.5), tracing (unless `PW_NO_TRACE`), page adoption — active = the first existing page (CDP: the user's open tab; launch: a fresh one), `pages[]` tracks all (M9.4 A6 unchanged). ⚠ **Amended by ADR-128:** the active page is always OURS, and `pages[]` holds only it plus the popups it raised; the user's tabs never enter it. **In CDP mode** these env-gated side effects (header route-injection + tracing) apply to the user's **live session** — set `PW_NO_TRACE=1` to avoid recording it into `trace.zip`.
- **Teardown guard:** an `attachedOverCDP` flag — in CDP mode we do **not** close the user's browser (neither in the `server.ts` cleanup nor in the SIGTERM handler): we just exit, which drops the CDP connection and leaves Chrome alive.

### Determinism (ADR-037)
- **Golden replay is deterministic in headless Chromium only.** Headed and CDP-attach are **observation / live-drive** modes: a different render path + (CDP) the user's viewport/context mean screenshot bytes are **not** stable. By design (see `docs/DETERMINISM.md`).

### Engine (ADR-036)
- **Chromium-only by design.** `connectOverCDP` is Chromium-only; golden hashes differ per engine. Firefox/WebKit are a separate decision-first milestone (**GAP-OPS-001**), deferred.
