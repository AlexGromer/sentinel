# Self-Healing — Sentinel

> 🌐 **Русский** (основная версия) · [English](SELF_HEALING.en.md)

> Составлено по результатам проектного синтеза 2026-06-23; итоговое описание — в ../ARCHITECTURE.md.

**Область применения:** данный документ описывает полный пайплайн самовосстановления
(`HealingEngine.heal`, `brain/healing.py`). Он выполняется **не** в графовом узле `heal`
(тот в explore-графе — заглушка), а в standalone-цикле `run_replay()` (`brain/replay.py`),
который вызывает `heal.heal(ctx)` при живом отказе локатора. Вход `ctx` — обычный dict
(`brain/replay.py:207-210`): `{step, semantic_id, page_path, intent, attempted_locator,
alternatives, dom_hash, interactives}`. Пайплайн ограничен, откалиброван, «проверять перед принятием».

**Замечание по интерфейсу браузера (BUILD_ONLY_DELTA):** Все упомянутые ниже вызовы MCP-инструментов
(`accessibility_snapshot`, разрешение/зондирование локаторов, screenshot) направляются в **`pw-executor`** —
наш собственный TypeScript-сервер выполнения Playwright, который мы СОЗДАЁМ, реализующий stdio-интерфейс
MCP/JSON-RPC-2.0. Транспорт MCP-over-stdio идентичен любому другому MCP-серверу; `pw-executor` —
это специализированная реализация, а не готовый продукт.

---

## Шаг 1 — Триггер восстановления

Классификатора сбоя в четыре класса (`LOCATOR_STALE`/`ELEMENT_GONE`/`TIMING`/`UNEXPECTED_ERROR`)
в коде **нет**. Реальный триггер один и живёт в `run_replay()` (`brain/replay.py:194-198`): для шага
с локатор-глаголом выполняется `browser.probe` по замороженному первичному локатору, и если он
**не** резолвится ровно в 1 элемент (`count != 1`), запускается `heal.heal(ctx)`. Шаги без локатора
(навигация и т.п.) восстановлению не подлежат.

---

## Шаг 2 — Обновление восприятия

Не использовать устаревший снимок из предыдущего цикла.

1. Выполнить свежий вызов `pw-executor` → `accessibility_snapshot()`.
2. Взять текущие интерактивные элементы страницы (`current_elements`) для передачи в reground.
3. При необходимости сделать снимок экрана через `pw-executor` → `screenshot()` для шлюзуемой визуальной
   попытки на Шаге 6.
4. Пересчитать `dom_hash = _a11y_hash(ariaSnapshot)[:16]` — хеш a11y-снимка **всей страницы**
   (`brain/replay.py:210`; это же значение — ключ кэша `dom_subtree_hash`). Признака
   `completeness_ratio` в коде нет.

Свежий снимок предотвращает восстановление относительно состояния DOM, которое к моменту
heal-цикла уже могло снова измениться.

---

## Шаг 3 — Поиск в кеше (нулевой LLM)

Запросить `store-gateway` → `Lookup(LocatorKey{page_path, semantic_id, dom_subtree_hash})`,
где `status = active`.

**Попадание в кеш:** если запись существует **и** её сохранённый `dom_subtree_hash` совпадает
с текущим хешем поддерева → **немедленно использовать повторно**. Это эффект амортизации:
LLM оплачивается один раз; восстановленный локатор переиспользуется во всех запусках replay
до обнаружения структурного дрейфа.

**Промах кеша / несоответствие хеша:** выгрузить устаревшую запись (пометить `deprecated`)
и перейти к Шагу 4. Это автоматическое вытеснение предотвращает молчаливое распространение
устаревшего локатора.

На этом шаге токены LLM не расходуются.

---

## Шаг 4 — Ротация стратегий L1–L6 (нулевой LLM, детерминированная)

Для проблемного намерения построить кандидатные локаторы и **зондировать** каждый в живом DOM
через разрешение MCP-локаторов `pw-executor`. Выбрать **первого кандидата, разрешающего в ровно один элемент**.

| # | Стратегия | Форма селектора | Базовый prior |
|---|---|---|---|
| L1 | атрибут `data-testid` / `data-cy` / `data-pw` | `[data-testid="…"]` | **0.95** |
| L2 | ARIA role + доступное имя | `role=button[name="Submit"]` | **0.90** |
| L3 | точное совпадение `aria-label` | `[aria-label="…"]` | **0.88** |
| L4 | Видимый текстовый контент + role | `text=Sign in >> role=link` | **0.80** |
| L5 | Ограниченный CSS — семантический контейнер + тип элемента | `.form-login input[type=email]` | **0.65** |
| L6 | Позиционный XPath | `//table/tbody/tr[2]/td[1]` | **0.45** |

Успешное совпадение на **L5 или L6** генерирует метрику `strategy_degradation` — сигнал того,
что AUT имеет нестабильную структуру DOM и требует внимания команды разработки.

Если на каком-либо уровне L1–L6 получено уникальное совпадение, значение уверенности из таблицы
выше передаётся на Шаг 7 (Verify-Before-Accept). Токены LLM не расходуются.

## Шаг 5 — Повторное связывание через LLM (модель heal по умолчанию Sonnet 4.6, структурированный вывод)

> **M6 (ADR-019):** «Sonnet 4.6» здесь и ниже — **модель heal по умолчанию**, маршрутизируемая
> через `LLMBackend` (`brain/llm.py`). Любой OpenAI-совместимый провайдер подключается через
> переменные `LLM_*_HEAL` (`LLM_BACKEND_HEAL`, `LLM_BASE_URL_HEAL`, `LLM_MODEL_HEAL`, …).
> Путь LLM — best-effort; при отсутствии ключа heal откатывается на детерминированную ротацию L1–L6.

Вызывается **только если Шаги 3–4 оба не дали** уникального совпадения в живом DOM.

**Предварительная проверка бюджета:** проверить остаток бюджета токенов модели heal (по умолчанию Sonnet) перед вызовом модели.
Если бюджет исчерпан, сразу перейти к порогу уверенности на Шаге 8 с confidence = 0.

**Входные данные промпта:**
- `step intent` — намерение шага
- `element the step used to use` — не сработавший `attempted_locator`
- `elements on the page now` — текущие интерактивные элементы страницы, **каждый со своим индексом**

(промпт `brain/healing.py::_llm_reground` шлёт ровно эти три поля; таблицы неудавшихся стратегий и `element_description` в нём нет)

**Вывод модели** (структурированный JSON, схема `_SCHEMA_PICK` — ИНДЕКС в списке элементов,
без самостоятельно заявленных `confidence`/`reasoning`/`strategy`):
```json
{"index": 2}
```
или, если ни один элемент не может служить цели шага:
```json
{"none": true}
```

С **ADR-082** модель выбирает среди элементов, о которых исполнитель реально сообщил, вместо
авторства CSS-селектора — то же правило заземления, которому всегда следовал планировщик
(ADR-022/027, `candidates[idx]`). Индекс вне диапазона отбрасывается, поэтому никакой ответ не
породит локатор для элемента, которого никто не наблюдал. Дескриптор выбранного элемента и
становится локатором (`testid`, иначе `role`+`name`) — и именно он сравнивается с замороженным
локатором на Шаге 7.

Промпт спрашивает, какой элемент теперь служит ТОЙ ЖЕ ЦЕЛИ, а не какой «соответствует намерению».
Формулировка несущая, и это доказал живой прогон: на второй вопрос и qwen3:14b, и qwen2.5vl:7b
отвечали `{"none": true}` на любое переименование — буквально правильно, ведь ни один элемент
больше не носит того имени, отчего шаг и упал. Предложить кандидата — работа тира; решить, тот ли
это элемент, — работа проверки тождества.

**Применяемая скидка:** модель не сообщает собственную уверенность — скидка применяется к prior
ТИПА получившегося локатора: `final_confidence = PRIORS[testid|role_name] × 0.90` (0.855 либо 0.81).

**Практическое следствие:** оба значения выше порога ПОМЕЧЕНО (0.60) и кэпируются ниже AUTO
правилом ADR-080 — то есть текстовая переоснова применяется ОПТИМИСТИЧНО и о ней сообщают.
До ADR-082 тир давал `PRIORS["css"] × 0.90 = 0.585`, ниже порога ПОМЕЧЕНО, и не чинил НИЧЕГО
никогда — при этом глуша visual-тир ниже, к которому `heal` переходит только `if not chosen`.

Скорректированная уверенность передаётся на Шаг 7.

## Шаг 6 — Визуальный Set-of-Marks (vision-модель heal по умолчанию Sonnet 4.6) — ШЛЮЗУЕМЫЙ

Этот шаг достигается и выполняется только при **прохождении всех трёх условий**:

1. `completeness_ratio < 0.30` (a11y-дерево разреженное — canvas, shadow DOM, кастомные компоненты)
2. Шаг 5 (повторное связывание через LLM) не дал валидного кандидата
3. M5 PoC подтверждён с **точностью > 70%** не менее чем на 20 реальных сценариях с нерабочими
   селекторами (шлюз по умолчанию отключён до получения измерения в M5)

> **M6 vision-gating (ADR-019, см. M6_CONTRACT.md §Vision-gating):** этот шаг (Tier-7 set-of-marks)
> дополнительно требует **vision-способного backend** — эффективный гейт `use_visual AND backend.supports_vision`.
> Text-only провайдер (например, DeepSeek-V3) **пропускает Tier-7** и деградирует
> в детерминированную ротацию L1–L6.

**Механизм:**
- На снимке экрана, сделанном в Шаге 2, отрисовываются нумерованные метки-оверлеи.
- Строится карта `mark → DOM-element` (номера меток к семантическим узлам a11y-дерева).
- Vision-модель heal по умолчанию (Sonnet 4.6) получает аннотированный снимок и возвращает
  JSON `{"mark": <int>}` (номер выбранной метки) или `{"none": true}` — без самостоятельно
  заявленной уверенности.
- Из сопоставленного узла DOM извлекается **реальный семантический локатор** — **не** координатный клик.
  Координатные клики ненадёжны при изменениях размера viewport, device-pixel-ratio и позиции прокрутки.

**Уверенность:** модель не сообщает confidence — используется FIXED-значение базового prior
стратегии `visual`: `final_confidence = PRIORS["visual"] = 0.80` (без какой-либо скидки).

**Практическое следствие:** 0.80 удовлетворяет порогу ПОМЕЧЕНО (0.60), но никогда не достигает
порога АВТО-ВОССТАНОВЛЕНИЕ (0.85) → визуальное повторное связывание, если кандидат проходит
проверку на Шаге 7, **всегда** попадает в `flagged` — оно никогда не автоматизируется полностью.

## Шаг 7 — Проверка перед принятием (повторное зондирование живого DOM)

**Каждый кандидат, созданный на Шагах 5 или 6**, повторно проверяется в **живом DOM**
через разрешение локаторов `pw-executor`, прежде чем доверять каким-либо значениям уверенности.

- Если кандидат **не разрешается в ровно один элемент**: `confidence = 0` (обнуляется, а не
  применяется скидка — он просто ошибочен).
- Если кандидат разрешается в ровно один элемент: подтверждается скорректированная уверенность
  из Шага 5 или 6.

```
final_confidence = max(confidence values that passed the live-probe check)
```

Кандидаты из Шага 4 (L1–L6) уже зондируются в живом DOM во время ротации — они не требуют
повторной проверки здесь. Только кандидаты LLM и визуальные (Шаги 5–6) проходят через этот шлюз.

Этот шаг устраняет разрыв между «модель говорит, что локатор работает» и «локатор действительно
работает прямо сейчас».

### Тождество (ADR-082) — вторая половина того же шага

Проверка количества устанавливает, что совпал ОДИН элемент. Она не устанавливает, что это ТОТ ЖЕ
элемент, и до ADR-082 этого не устанавливало ничто: переоснова могла привязаться к другому контролу,
а прогон отчитывался об обычной починке.

Для **переосновы** (стратегии, которую план не заморозил, — см. Шаг 8) дескриптор живого элемента
сравнивается с тем, что уже несёт замороженный локатор:

| Исход | Значение | Эффект |
|---|---|---|
| `verified` | живые `role` и нормализованное `name` равны замороженным | применяется; деградация не сообщается |
| `contradicted` | различаются — контрол переименован либо это другой контрол | **всё равно применяется**, и сообщается как деградация (`heal.identity_contradicted`) |
| `unverifiable` | план не заморозил имени (первичный локатор только с testid) либо тир ничего не сообщил | применяется; сообщается как `heal.identity_unverifiable` |

Это **предикат, а не оценка**: порога нет намеренно — `PRIORS` признаны неизмеренными в самом этом
файле (GAP-RISK-002), и порог похожести стал бы вторым некалиброванным числом рядом с первым.

Сравнение **строже пробы, которая породила кандидата**: `buildLocator` передаёт `{name}` в
`getByRole` без `exact`, поэтому Playwright матчит без учёта регистра и по подстроке — `"Pay"`
удовлетворяется `"Pay now"`. Равенство — нет.

**Переприязка** пометки тождества не несёт вовсе: за замороженный ключ ручается план, и выдумывать
здесь сомнение было бы так же нечестно, как скрывать его на переоснове.

**Что это НЕ закрывает:** два контрола, действительно неразличимых по роли и имени (две кнопки
«Add to cart» в списке), проверку пройдут даже при привязке к неверному. Это вопрос «тот же ли
ЭКЗЕМПЛЯР», и ответить на него могло бы только окружение — зато случай стал счётным
(`probe_count >= 2` доезжает в heal-контекст), а это и есть тот размеченный сигнал, который
понадобится будущему механизму.

## Шаг 8 — Порог уверенности (откалиброванный, не магический)

Значение `final_confidence`, вычисленное на Шаге 7, оценивается относительно трёх уровней.
Пороги — FIXED-константы модуля (`AUTO, FLAG = 0.85, 0.60` в `brain/healing.py`), используемые
напрямую в шлюзе (`conf >= AUTO`, `conf >= FLAG`); в рантайме они не перекалибровываются.

| Диапазон уверенности | Решение | Поведение |
|---|---|---|
| **≥ 0.85** | **АВТО-ВОССТАНОВЛЕНИЕ** | Выполнить одну послевосстановительную проверку: повторно выполнить действие с восстановленным локатором. При успехе сохранить `HealedLocator(status=active)`, привязанный к `(page_url, semantic_id, dom_subtree_hash)`, обновить `RunState` и план в памяти, продолжить. При неудаче пост-проверки исход — `needs_review`/`failed` (строка ниже). |
| **0.60 – 0.84** | **ПОМЕЧЕНО** | Применить оптимистически (**не** блокирует выполнение — ADR-005/017) и **сказать об этом**: исход `flagged` едет в `heal-report.json` вместе с confidence, попадает в колонку «accepted as» таблицы дрейфа отчёта, помечается на кейсе JUnit и поднимает деградацию `heal.applied_unverified` на вердикт (ADR-077/080). ⚠ Историческая правка 2026-07-26: здесь значилось «сохранить с `review_required=true`» и «отображается в разделе аудита восстановления отчёта» — **ни того, ни другого не существовало**: `review_required` не встречался в репозитории ни разу, а `flagged` — ни в `report.py`, ни в `junit.py`, ни в UI. Починка применялась и молчала. Описанное выше — то, что реализовано ADR-080. |
| **< 0.60** | **`needs_review` / `failed`** | Локатор **не** сохраняется. Исход `needs_review` (нашли кандидата, но ниже порога) либо `failed` (кандидата нет) записывается в таблицу `healing_audit` и попадает в heal-report. Отдельного per-heal-CLI `agentctl gate` **нет** (не существует в коде); живой человеческий takeover — это отдельный механизм `takeover`-узла (`interrupt`/`Command(resume)`, ADR-054), валидируется на M9-LIVE. |

**Отчётность по калибровке — `cold_start` (по умолчанию 0.90):** `brain/calibrate.py::calibrate()`
принимает параметр `cold_start=0.90`, но это значение — **только для отчётности**: оно попадает
в `state/calibration.json` (режим `RUN_MODE=calibrate`, офлайн-путь `_run_calibrate` в
`brain/__main__.py`) как справочная метрика рядом с гистограммой `confidence`. `healing.py`
ничего не импортирует из `calibrate.py`; живой шлюз всегда использует FIXED 0.85/0.60 (см. выше) —
никакой обратной связи «порог снижается к 0.85 по мере накопления сигнала» в коде нет.

## Шаг 9 — Аудит (только добавление)

Каждая попытка восстановления — независимо от результата — записывает одну строку в `healing_audit`.
Таблица содержит **только добавление**: ни одного `UPDATE` или `DELETE` к ней никогда не применяется.
Это делает аудит криминалистически достоверной записью и источником истины для калибровки.

**Схема строки:**

| Столбец | Тип | Описание |
|---|---|---|
| `run_id` | uuid | UUID запуска, инициировавшего данную попытку восстановления |
| `step` | int | Индекс шага в плане |
| `semantic_id` | str | Семантический идентификатор элемента |
| `original_selector` | str | Селектор, который не сработал |
| `strategy_used` | enum | `testid` \| `role_name` \| `label` \| `text_role` \| `css` \| `xpath` \| `visual` \| `none` (см. `PRIORS`, `healing.py:26-27`; `none` — при полном отказе на Шагах 4–6) |
| `healed_selector` | str | Кандидатный селектор (может быть `null` при полной неудаче) |
| `confidence` | float | Итоговая уверенность после скидок и проверки в живом DOM |
| `outcome` | enum | `cache_hit` \| `auto_healed` \| `flagged` \| `needs_review` \| `failed` |
| `llm_tokens` | int | Токены, потреблённые Шагами 5–6 (0 для путей cache/L1–L6) |
| `duration_ms` | int | Реальное время выполнения полного heal-цикла |
| `dom_hash_before` | str | Хеш поддерева в момент сбоя |
| `dom_hash_after` | str | Хеш поддерева после свежего восприятия (Шаг 2) |
| `timestamp` | datetime | UTC-временная метка попытки |

Таблица `healing_audit` выгружается как CI-артефакт `healing-audit.jsonl` и как атрибуты
OpenTelemetry span (только поля `selector` и `confidence` — **никогда** не содержимое промптов,
во избежание утечки учётных данных AUT, которые могут присутствовать в a11y-дереве).

## Шаг 10 — Ограниченные повторы и карантин

### Однократный вызов — без лимита попыток

Как построено: лимита `heal_attempts` не существует. У heal-цикла нет счётчика повторов —
каждый шаг вызывает `HealingEngine.heal()` не более одного раза за попытку действия:

- **Explore:** узел `heal` в графе LangGraph (`brain/graph.py`) — **заглушка**: он не выполняет
  никакого реального восстановления, только инкрементирует счётчик `consecutive_heal_failures`
  для сигнала авто-HITL (M14, ADR-055) и передаёт управление в `checkpoint`. Реального связывания
  в explore-режиме не происходит вовсе.
- **Replay / CI:** `brain/replay.py` вызывает `heal.heal(ctx)` **ровно один раз** на неудавшийся
  шаг (без цикла повторов). Результат применяется, если `outcome` — `auto_healed`, `flagged` или
  `cache_hit`; иначе шаг помечается `failed`.

### Карантин нестабильных тестов с учётом AUT SHA

Шаг помещается в карантин только при выполнении условия шлюза:

> Шаг завершается неудачей в **N из 5** последних запусков **без** изменения `git-SHA` AUT между этими запусками.

Это разделяет два различных режима сбоев:
- **Реальная регрессия:** сбой локатора коррелирует с изменением кода AUT → проявляется как exit 1/2,
  не попадает в карантин, должна быть устранена.
- **Нестабильность окружения:** повторяющийся сбой без изменения AUT → карантин, не блокирует.

**Поведение при карантине:**
- Помещённые в карантин шаги всё равно выполняются в каждом запуске.
- Они **не** влияют на коды завершения 1 или 2.
- Они видны в отчёте запуска в отдельном разделе карантина.
- **Снятие карантина:** `agentctl locators clear-quarantine <step>` или 3 последовательных
  прохождения на одном и том же AUT SHA.

Это правило взято из P3 (TrustFirst) как наиболее чистый механизм разделения реального сигнала
регрессии от шума окружения без подавления реальных сбоев.
